      • msg1Size

        Parameters:

      • padding1Max

        static int padding1Max(int version)
        Upper bound (exclusive) for the message 1 padding we send, per version, equal to i2pd's maxPaddingLength in CreateSessionRequestMessage: offset + 32 for a PQ frame, clamped so the whole message fits i2pd's 2528-byte handshake budget (944 + MLKEM-1024 key + 16), which is what pulls MLKEM-1024 back down to 880. Version 2 takes i2pd's short bound: i2pd only uses long padding once the peer advertises PQ support (its pq address option), and we reach versions 3-5 for exactly those peers, so a peer predating the 2026 padding increase (Java _X = 256, i2pd m_Buffer = 287) never sees more than 222 bytes from us. Taking i2pd's value for every version also keeps our handshake size distribution the same as theirs.
        Parameters:
        version - the negotiated NTCP2 intro version
        Returns:
        exclusive upper bound for padlen1 (longest padding = value - 1)

      • padding1RecvMax

        static int padding1RecvMax(int version)
        Largest message 1 padding we accept, per session version. Never below padding1Max(int): i2pd's Alice drops to a non-PQ session one time in four (ClientLogin) but keeps long padding because the peer advertises PQ, so a version 2 session may legally carry 880 bytes of padding even though we would only ever send 223 there.
        Parameters:
        version - the negotiated NTCP2 intro version
        Returns:
        inclusive maximum padlen1 a peer may announce

        static int padding2Max(int version)
        Upper bound (exclusive) for the message 2 padding, in both directions, equal to i2pd's maxPaddingLength in CreateSessionCreatedMessage (offset + 32, clamped by the same 2528-byte budget). Bob applies it only when Alice used long padding, otherwise PADDING_SHORT_MAX.

      • msg2PaddingMax

        static int msg2PaddingMax(int version, int padlen1)
        The padding cap for message 2, scaled to what Alice sent. i2pd's Bob uses long padding only when Alice's message 1 came in longer than the short handshake - ProcessSessionRequestMessage sets m_IsLongPadding - so a peer that kept its message 1 small gets a small answer back, and our reply lands in the same size class as i2pd's Bob.
        Parameters:
        version - the negotiated NTCP2 intro version
        padlen1 - the padding Alice announced in message 1
        Returns:
        exclusive upper bound for padlen2 (longest padding = value - 1)

      • msg1PayloadOffset

        static int msg1PayloadOffset(int version)
        Offset of the plaintext options block within the message 1 buffer. For versions 3-5 the Noise F token - the ML-KEM encapsulation key and its MAC - is written between X and the options, so the options have to be staged past it: writeMessage() lays down the F token first and only then reads the payload, so staging them at KEY_SIZE makes it encrypt the key material instead, and the peer gets a valid-looking tag over garbage options. For version 2 this is KEY_SIZE, as it always was.
        Parameters:
        version - the negotiated NTCP2 intro version
        Returns:
        offset of the options block within message 1
