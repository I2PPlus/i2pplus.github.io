    public class Tunerextends SimpleTimer2.TimedEvent
    General-purpose adaptive tuner. Observes network and system stats, adjusts tunable parameters to optimize router performance.

    Runs every 5 seconds via SimpleTimer2. Each tick samples transport worker-stage CPU and updates the transport thread pool params; every 15th-second tick runs the full cycle for all other params. Each parameter implements an AIMD-style feedback loop bounded within safe ranges:

    1. Read observed stat (60s rolling average)
    2. Compute target value from observed stat + cross-references
    3. Clamp target to [min, max]
    4. Apply health-based dampening when system is degraded
    5. Accelerate rollback when param diverges from default
    6. Call applyValue() to push the new value to the router

    New parameters are added by extending Tuner.BaseParam and implementing:

    • applyValue(int) — push value to router subsystem
    • getRuntimeValue() — read current value from subsystem
    • getObservedStat(RouterContext) — read primary signal
    • computeTarget(double) — feedback logic with cross-refs

    Params can be tuned live via the console UI or persisted to autotune.config (separate from router.config). Auto-revert to factory defaults triggers when system health drops below 0.3.

      • ESTABLISH_TIMEOUT_MIN

        public static final int ESTABLISH_TIMEOUT_MIN
        Lowest value either establish-timeout param may be tuned to.

        Measured on a live router: at 2250 the outbound path abandoned roughly 117 session establishments per minute, every one expiring on the deadline rather than on an observed peer failure, and 99.6% of them inside the SSU2 token exchange, which costs one round trip more than SSU1. Raising the budget to 5000 took that to zero - but build success fell from 64.5% to 56.0% and throughput 12%, because the patience moves out of the establishment path and into the build slot. 4000 is the compromise: comfortably above the value known to be harmful, below the one where slot occupancy starts costing builds. The original floor of 1500 sat well below the harmful value, so a slider drag or a restore-defaults could silently reintroduce the failure.

      • establishTimeoutTarget

        static int establishTimeoutTarget(double observed, int min)
        Target establish timeout for an observed mean handshake duration.

        Four times the observed mean, floored by the param's own minimum. The floor must come from min rather than a literal: a hardcoded floor here can sit far below the value the setter enforces, and Tuner.BaseParam.clamp(int, int, int) walks the stored value toward the target by _step without consulting min at all - so the stored value would drift down while the runtime value stayed clamped, leaving the console permanently displaying a number the router was not using.

        Parameters:
        observed - mean successful handshake duration in ms, or NaN if unknown
        min - the param's configured minimum
        Returns:

      • computeStreamingMaxWindowTarget

        static int computeStreamingMaxWindowTarget(int current, int min, int max, int step, int defaultValue, double failLifetime, double lossRate, double memPct)
        Compute the streaming max-window ceiling target for one tuning cycle.

        The ceiling bounds in-flight messages per connection. It is an upper bound, not a reservation — in-flight data still tracks the ACK-driven congestion window — so a high ceiling never loads a slow path; it only removes a throttle from a fast one.

        The former logic additionally shrunk the ceiling whenever the bandwidth-delay product fell below current, but that bandwidth is measured through the current ceiling: on a capped connection a low average is an artifact of the cap, not evidence the cap should drop, and ratcheting the cap down on that artifact produced a down-only spiral (a sub-ceiling bandwidth read-out justifies shrinking the cap, which lowers the read-out further, ...).

        The ceiling therefore shrinks ONLY on hard negative signals (duplicate retransmits, gateway congestion, memory pressure) and climbs on a clean path, bounded upward and gated on heap headroom so a large jump can never be the event that pushes the heap into pressure.

        The clean-path climb is hyper-responsive: with strong headroom (heap below 40%) it takes four steps per cycle, with moderate headroom (below 50%) two, and at 50% or above it holds until memory frees rather than spending headroom it may need. Combined with the 5s fast cycle, the 8192-message ceiling is reachable from the factory default in four strong cycles (~20s) instead of ~4 slow minutes; every climb is still bounded by max and scaled down by health dampening in BaseParam.update().

        Below the recovery floor (max(min, defaultValue / 2)) and otherwise healthy, the ceiling climbs two steps toward the factory default; under hard signals it shrinks half a step but never below the recovery floor, so a depression cannot be torn back down to the floor trim. Shrinking is deliberately the fastest way to lose headroom: loss, congestion, or heap above 60% all pull the ceiling back within one (fast) cycle.

        current - current ceiling value (Connection#getGlobalMaxWindowSize)
        min - lower bound for the ceiling (inclusive)
        max - upper bound for the ceiling (inclusive)
        step - one tuning step; clean-path climbs use four steps under strong heap headroom and two otherwise, hard-signal shrinks use half a step
        defaultValue - factory default ceiling; the recovery floor is max(min, defaultValue / 2)
        failLifetime - stat transport.sendMessageFailureLifetime in ms, or NaN if absent
        lossRate - streaming retransmission rate (0.0-1.0), or NaN if absent; see streamingLossRate(double, double, double, double)
        memPct - stat jobQueue.memoryUsedPercent, or NaN if absent
        Returns:
        the new ceiling target within [min, max]

Above 90% the step doubles the current budget so a download burst cannot wait out a +2-per-cycle crawl; between 70–90% growth is still aggressive. Below 20% the budget shrinks by one so a quiet router does not hold threads it does not need.

        Parameters:
        current - current runtime budget (clamped to [min,max] first)
        observed - the busiest pool's utilization rate; NaN or negative leaves the value unchanged
        min - inclusive lower bound
        max - inclusive upper bound
        Returns:
        target budget in [min, max]

      • nextStallTimeoutMs

        static int nextStallTimeoutMs(int current, double observed, int minMs, int maxMs)
        Next I/O stall window for an observed per-cycle stall delta.

        Pure, so the policy is testable without a router.

        The window only loosens above the floor when transfers are being cut off, and relaxes back to the floor when they are not. It never goes below the floor, and there is deliberately no "no stalls, tighten" branch: a shorter window kills more legitimate transfers, which produces more stall events, which loosens the window, which then tightens again on the next quiet cycle. That limit cycle parked the window at its 5s floor, shorter than any pause in a bulk transfer, and aborted 45MB downloads partway through.

        Parameters:
        current - the window in effect, ms
        observed - stall events in this cycle
        minMs - the floor in ms; a negative value is raised to 0
        maxMs - the ceiling in ms; the returned window never exceeds it
        Returns:
        the next window, ms

      • computeServerBacklogQueueCapacity

        static int computeServerBacklogQueueCapacity(int current, int min, int max, double queueDepth, double jobLag)
        Pure decision logic for the I2PTunnel server handler queue capacity. Extracted (package-visible, static) so unit tests can exercise the policy without a live RouterContext.

        The queue is the admission buffer between the accept loop and the handler pool. queueDepth (60s avg) is how deeply it is actually used. Growing it widens the burst window; shrinking it bounds memory (each queued task holds an I2PSocket).

        Signals:

        • queueDepth — handler tasks waiting for a free pool thread.
        • jobLag — jobQueue.jobLag as a CPU-pressure veto: never grow the buffer on a swap/busy box.

        Idle handling converges the buffer to SERVER_BACKLOG_IDLE_FLOOR rather than to min: a too-large buffer shrinks, a too-small one grows, so a quiet server retains a burst buffer and can never be parked at the hard 16 floor. min remains only the external setter clamp.

        Parameters:
        current - current queue capacity
        min - the setter's lower clamp, unused here; the idle floor sets the low end instead
        max - the ceiling every growth branch clamps to
        queueDepth - 60s avg of i2ptunnel.serverHandler.queueDepth, or NaN
        jobLag - 60s avg of jobQueue.jobLag, or NaN
        Returns:
        the new queue capacity

      • isHealthyBuildRate

        static boolean isHealthyBuildRate(double observed)
        Whether a build success rate counts as healthy for a tuning walk.

        Four params gate their walk on observed > 80: the first-hop cooldown, first-hop threshold, stale-build threshold and concurrency throttle. This router runs 70-77% success, so all four saw "not healthy" permanently while their paired timeoutsHigh condition was also permanently true, and each walked to one of its bounds and stayed there -- the cooldown pinned at its 600s ceiling while the concurrency throttle sat at its 50% maximum.

        80% is a healthy-I2P target, not this network's operating point, so using it as a walk gate means the gate never opens. 50% still separates the broken case (single digits) from the working one without demanding a target this network cannot reach.

        Parameters:
        observed - build success rate as a fraction, or NaN when unavailable
        Returns:
        true when the rate is at or above the walk's healthy bound
