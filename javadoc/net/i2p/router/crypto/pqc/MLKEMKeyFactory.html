    public class MLKEMKeyFactoryextends I2PThread implements KeyFactory
    Try to keep key pairs at the ready. It's important to do this in a separate thread, because if we run out, the pairs are generated other threads, and it can fall behind.

    Started by ECIESAEADEngine. One type per-thread. Only used for 768, for now.

      • boundedPoolSize

        static int boundedPoolSize(int minSize, int demandMax, int cap)
        Bound a pool size: at least four above the floor, never above the cap.

        The floor is capped too, so a configured minimum larger than the cap cannot smuggle the pool past the byte budget by way of the floor.

        Pure and static so the byte budget's reach can be pinned without running the precalc thread.

        Parameters:
        minSize - the pool floor the pool must stay above
        demandMax - the size the caller wants, from demand or configuration
        cap - the ceiling, in keypairs
        Returns:
        the size to use, always ≤ cap

      • poolFloor

        static int poolFloor(int minSize, int cap)
        The smallest size the pool may be driven to: its floor, never above the cap. A floor set at the cap pins the pool there instead of letting every "at least min + 4" margin push it past the byte budget.
        Parameters:
        minSize - the pool floor
        cap - the ceiling, in keypairs
        Returns:
        the effective floor, always ≤ cap

      • refreshPoolSize

        public void refreshPoolSize()
        Called by the Tuner every 15 seconds. Adjusts max pool size based on demand.

        Demand is bounded by the byte budget, not by HARD_MAX: the earlier bound let demand drive the pool to 32768 pairs, roughly 128 MB, and the memory-pressure halving below only engages above 70% pressure, so a router with a large heap could sit there indefinitely.

      • pressureAdjustedMax

        static int pressureAdjustedMax(int maxSize, int minSize, int cap, double memPressure)
        Shrink the pool ceiling under memory pressure, without letting the shrink raise it past the byte budget on its way back down.

        The floor of each shrink goes through poolFloor(int, int), so a floor set at the budget cannot add its four-pair margin on top of the cap.

        Pure and static so the pressure branches can be pinned without driving the JVM's free-memory ratio.

        Parameters:
        maxSize - the ceiling demand produced
        minSize - the pool floor
        cap - the ceiling, in keypairs
        memPressure - the fraction of the heap in use, 0 to 1
        Returns:
        the ceiling to use, never above cap
