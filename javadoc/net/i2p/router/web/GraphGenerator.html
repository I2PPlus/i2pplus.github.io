    Runnable, ClientApp
    public class GraphGeneratorextends Object implements Runnable, ClientApp
    A thread started by RouterConsoleRunner that checks the configuration for stats to be tracked via jrobin, and adds or deletes RRDs as necessary.

    This also contains methods to generate xml or graph image output. The rendering for graphs is in GraphRenderer.

    To control memory, the number of simultaneous renderings is limited.

      • refineForIdleRate

        static GraphGenerator.StaleCause refineForIdleRate(GraphGenerator.StaleCause cause, long lastEventCount)
        Split "the rate has nothing to say" out of the causes that lose data.

        A listener that has never written, or has stopped writing, looks identical whether its RRD writes are failing or whether nothing in the router is feeding its rate at all. Only the first loses data. Event count settles it: a rate with no events in its last completed period had nothing to hand the listener, so there is nothing being lost.

        Event count rather than coalesce count, deliberately. Coalescing is driven by the StatManager sweep and happens on schedule whether or not any data arrives, so it keeps advancing for a rate nobody is updating. That made the coalesce form unable to distinguish "idle" from "fed but unwritten" for any listener that had been running, which is precisely the case a stopped service produces.

        Parameters:
        cause - classification from classifyStaleness(boolean, boolean, long, long, long, long)
        lastEventCount - events the rate accrued in its last completed period, or 0 when it accrued none
        Returns:
        GraphGenerator.StaleCause.RATE_IDLE when the rate produced no events in its last period, otherwise cause unchanged

      • isCoalesceSweepStalled

        static boolean isCoalesceSweepStalled(long sweepAgeMs)
        Whether the coalesce sweep has missed enough cycles that no rate can be recording.

        Pure threshold test, separated from the manager lookup so it can be pinned by unit tests. A sweep is considered stalled once it is older than twice the shortest rate period: the coalesce timer runs every 50s and the shortest period is one minute, so two missed sweeps is already unambiguous.

        Parameters:
        sweepAgeMs - ms since the last completed sweep, or -1 if none ever has
        Returns:

      • isCoalesceStalledNow

        static boolean isCoalesceStalledNow(boolean everSwept, long sweepAgeMs, long startedMs, long now)
        Whether the shared coalesce sweep should be reported as stalled right now.

        Separate from isCoalesceSweepStalled(long) so the start-up window can be pinned by tests. Until a sweep has ever completed its age is reported as -1, meaning "none ever", which that function quite correctly calls stalled. At start-up, though, that is not a fault - it is a sweep that has not come round yet, because the coalesce timer only fires every Router.COALESCE_TIME. Judging it as stalled made every boot log an ERROR naming the coalesce timer as the fault within seconds of start-up, and pointed the operator at the one subsystem the evidence could not implicate.

        Parameters:
        everSwept - whether any sweep has completed since graphing began
        sweepAgeMs - ms since the last completed sweep, or -1 if none ever has
        startedMs - wall-clock ms when graphing began
        now - current wall-clock ms
        Returns:
        true only once a sweep should have come round and has not

      • formatCoalesceSweepAbsence

        static String formatCoalesceSweepAbsence(long sweepAgeMs, long startedMs, long now)
        Render how long the coalesce sweep has been absent.

        Pure, so the sentinel handling can be pinned by test. The bug this exists to prevent: the accessor reports an unknown age as -1, and an earlier version interpolated that straight into the operator-facing ERROR, producing the nonsensical "has not completed for -1s". A negative duration is not a duration. The unknown case is now reported as the age of the graphing window and labelled, which is a real lower bound on the absence.

        Parameters:
        sweepAgeMs - ms since the last completed sweep, or negative if none ever has
        startedMs - wall-clock ms when graphing began
        now - current wall-clock ms
        Returns:
        a duration that always begins with a non-negative number of seconds

      • needsRevive

        static boolean needsRevive(boolean mapped, boolean detached, boolean registered)
        Does a configured rate need a listener rebuilt?

        Three distinct faults, each of which leaves the rate unrecorded for the rest of the router's life while every observable state still reads healthy: the RRD was closed after repeated write failures (detached), the map lost its listener (mapped false), or a newer listener took the Rate's single registration so this one can never be called again (registered false).

        Parameters:
        mapped - false if the rate has no listener entry at all
        detached - true if the listener's RRD is closed
        registered - true if the Rate still points at the listener
        Returns:
        true if the rate needs a new listener

      • chooseHeal

        static GraphGenerator.HealAction chooseHeal(boolean mapped, boolean detached, boolean registered, boolean writable, boolean backfillable)
        Cheapest action that can restore recording for one rate.

        Pure decision logic, ordered cheapest first, so the cost ordering is pinned by unit tests rather than by reading the ladder at the call site.

        The first row is also the spec-churn guard: a listener that is mapped, attached and registered can only ever reach BACKFILL or NONE, never REOPEN or REBUILD, so re-reading a changed stat.summaries string cannot close and reopen a healthy RRD.

        Parameters:

        registered - true when the Rate still points at the listener
        writable - true when the handle can still take a write (not closed)
        backfillable - true when the rate still retains unstored samples
        Returns:
        the action to take, cheapest first

      • backfillWindow

        static int backfillWindow(long drift)
        How many retained samples one backfill attempt should ask for.

        Bounded by the drift, since asking for more steps than are missing wastes a list copy every tick, and capped at MAX_BACKFILL_STEPS so a listener that fell thousands of steps behind does not ask for a list that long - the accessor's own clamp would discard the excess anyway, and the excess is exactly the part that is permanently gone.

        Parameters:
        drift - coalesces minus stored steps
        Returns:
        number of retained samples to request, never below one

      • classifyDrift

        static GraphGenerator.DriftCause classifyDrift(int pending, long oldestPendingMs, long overruns, boolean coalesceAdvancing)
        Name the mechanism behind positive ledger drift.

        These are the three candidates that were indistinguishable from the console during the incident this exists for: a coalesce that never happened, a sample that queued and never drained, and a sample that arrived and was not written. Each has a different fix, so the report has to pick one.

        Pure, so the mapping from counters to mechanism is unit tested without a router, a StatManager or a clock.

        Parameters:
        pending - samples waiting for delivery
        oldestPendingMs - age of the oldest waiting sample
        overruns - samples evicted at the queue's hard cap
        coalesceAdvancing - whether any tracked rate coalesced recently
        Returns:
        the most specific cause the counters support

      • formatLedgerDrift

        static String formatLedgerDrift(int totalListeners, int drifters, long maxDrift, long permanentSteps, long healedSteps, int rebuilt, int reopened, long coalesced, GraphGenerator.DriftCause mechanism, long overruns, long superseded, int pending, long oldestPendingMs, long backlogCollapses, long coalesceSkips)
        Compose the ledger-drift log line.

        Pure and single-line, so the wording and the six StatManager counters can be asserted in a unit test. The counters are the point of the line: an operator reading "pending climbing with oldest-pending-age climbing" knows the consumer is wedged, "pending zero with a flat coalesce count" knows the rate stopped coalescing, and a climbing skip count points at the coalesce early return.

        Parameters:

        reopened - listeners reopened this tick

        mechanism - the named cause from classifyDrift(int, long, long, boolean)
        overruns - StatManager sample overruns
        superseded - StatManager same-step supersessions
        pending - StatManager delivery queue depth
        oldestPendingMs - StatManager age of the oldest queued sample
        backlogCollapses - StatManager coalesce backlog collapses
        coalesceSkips - StatManager coalesce skips
        Returns:
        a single-line message beginning "RRD ledger drift:"

      • getGroupListeners

        public List<GraphListener> getGroupListeners(String groupId, Set<String> enabledStats)
        Collect the listeners for the enabled members of a graph group.

        Members are returned in the group's legend order, not in listener order, so the colours and legend entries stay put as stats are enabled and disabled. Members whose RRD has not been created yet are skipped: a stat that has never been sampled has no series to draw, and including it would silently stretch the axis to zero.

        Parameters:
        groupId - a group id from GraphGroups
        enabledStats - stat names enabled by the user, without period suffixes
        Returns:
        the members that have data, in legend order; empty when fewer than two
