    Runnable, ClientApp
    public class GraphGeneratorextends Object implements Runnable, ClientApp
    A thread started by RouterConsoleRunner that checks the configuration for stats to be tracked via jrobin, and adds or deletes RRDs as necessary.

    This also contains methods to generate xml or graph image output. The rendering for graphs is in GraphRenderer.

    To control memory, the number of simultaneous renderings is limited.

      • HEALTH_INTERVAL_MS

        private static final int HEALTH_INTERVAL_MS
        Watchdog period.

        Short enough that the next occurrence of a silently dead data path names its own cause while somebody is still looking at the log, and long enough that a healthy router does no measurable work. Deliberately separate from the 90s sync task: a fault severe enough to wedge that task is exactly the fault the watchdog exists to report, so sharing a thread would hide the symptom it is looking for.

      • installRrdLogging

        private void installRrdLogging()
        Route rrd4j diagnostics into the router log.

        The vendored rrd4j in apps/jrobin is built without a classpath, so it cannot log through I2P itself and ships with all of its own logging stripped. That is why a permanently cancelled flush schedule produced no output at all: the .jrb files simply stopped changing. This installs the bridge so that failure is visible from now on.

      • startHealthWatchdog

        private void startHealthWatchdog()
        Start the 10s health watchdog, at most once.

        Idempotent on purpose: runGenerator() is the only caller and runs once, but a second scheduler would mean two threads applying the heal ladder to the same listeners concurrently, which is how a REOPEN ends up racing a REBUILD into a half-closed handle. Guarded here rather than trusted to the caller.

      • stopHealthWatchdog

        private void stopHealthWatchdog()
        Stop the health watchdog if one was started.

        Never called from a watchdog task: a scheduler that awaits its own termination from inside a task cannot terminate, and the bounded wait would become an unbounded stall.

      • refineForIdleRate

        static GraphGenerator.StaleCause refineForIdleRate(GraphGenerator.StaleCause cause, long lastEventCount)
        Split "the rate has nothing to say" out of the causes that lose data.

        A listener that has never written, or has stopped writing, looks identical whether its RRD writes are failing or whether nothing in the router is feeding its rate at all. Only the first loses data. Event count settles it: a rate with no events in its last completed period had nothing to hand the listener, so there is nothing being lost.

        Event count rather than coalesce count, deliberately. Coalescing is driven by the StatManager sweep and happens on schedule whether or not any data arrives, so it keeps advancing for a rate nobody is updating. That made the coalesce form unable to distinguish "idle" from "fed but unwritten" for any listener that had been running, which is precisely the case a stopped service produces.

        cause - classification from classifyStaleness(boolean, boolean, long, long, long, long)
        lastEventCount - events the rate accrued in its last completed period, or 0 when it accrued none
        Returns:
        GraphGenerator.StaleCause.RATE_IDLE when the rate produced no events in its last period, otherwise cause unchanged

        private void healthCheck()

        Holds no lock across I/O and does no RRD work itself beyond the backfill the ladder asks for. Wrapped in a Throwable catch because an escaping exception silences a fixed-rate scheduled task permanently, which would remove the very watchdog that is supposed to notice the data path dying.

      • applyHealLadder

        private void applyHealLadder()
        Walk every listener, heal what can be healed, and report what could not be.

        Iterates _listeners rather than the rate map so that "mapped" is a real question: a listener that is alive but has lost its map entry is exactly the REBUILD case the ladder exists for, and iterating the map would never see it. The map's own dead entries are handled by reviveDetachedListeners().

        The ledger reports at WARN, not ERROR, because it describes drift the ladder has usually already repaired, and a single INFO marks its clearing.
