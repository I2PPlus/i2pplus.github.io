      • filledLineWidth

        private float filledLineWidth(GraphRenderer.GraphRenderConfig cfg)
        Stroke width for the line overlaid on a filled plot.

        The line drawn over a filled area is not the plot line, so --graph_plotLineWidth and its plain, wide and condensed siblings do not apply to it; it has --graph_plotLineWidthFilled. It used to be half the plot width, which tied an edge that exists to keep the fill readable to a weight chosen for a line that is not being drawn.

        Reads only the filled family. An edge on a fill does not take its weight from the plot line it sits on - letting it track that meant the two could never be set apart - but it does answer the same three questions the plot line does, through its own plain, wide and condensed variables. The width test is shared with lineWidth(GraphRenderer.GraphRenderConfig) so the two families switch at the same frame width; the values are not shared.

        Parameters:
        cfg - the render configuration
        Returns:
        stroke width in pixels
        See Also:
        • GraphThemeColors.plotLineWidthFilled(File, String)

      • lineWidth

        private float lineWidth(GraphRenderer.GraphRenderConfig cfg)
        Stroke width for a plotted series.

        Three cases are decided here rather than by the theme, because each is a fact about one layout rather than a look the console wants:

        • Grouped graphs stack up to six lines on one axis and are drawn thinner so they stay separable and the dense case does not fill in.
        • The sidebar sparkline is drawn thick because it is small and unlabelled, and a hairline nearly vanishes at that size.
        • A tile carrying many periods is drawn thinner for the same reason the grouped case is: the series is crowded.

        Everything else - an ordinary plot, including one carrying a group of series - takes its weight from the theme. Grouping used to short-circuit to a hard-coded ALL_LINES_WIDTH of 1.5 before any variable was read, which meant --graph_plotLineWidth and --graph_plotLineWidthWide never reached a combined graph and a theme had no way to weight one. The theme now governs, and the constants left here are the cases where a layout reason, not taste, sets the weight: a bare sparkline that a hairline would erase, and a tile crowded enough that any weight merges the series.

        Parameters:
        cfg - the render configuration
        Returns:
        stroke width in pixels

      • isCondensedTile

        static boolean isCondensedTile(GraphRenderer.GraphRenderConfig cfg)
        Whether a tile is narrow and carrying condensed data, and so takes the theme's condensed plot width.

        Separate from isCrowdedTile(GraphRenderer.GraphRenderConfig) because the two answer different questions. A crowded tile has enough periods that any width merges the series, so it takes a fixed hairline. A condensed tile is merely narrow for the number of periods it carries, so the weight stays the theme's to set - thinner than an ordinary plot, but not a hairline.

        Deliberately independent of smoothing. Smoothing used to exempt a tile from this, because an unsmoothed polyline crowds where a rounded curve does not - but smoothing is itself only a default, and a stepped series is what a user asking for step gets. Gating on it meant the same tile was drawn at two different weights depending on a setting whose value nobody reading the graph could see.

        Parameters:
        cfg - the render configuration
        Returns:
        true if a narrow, period-dense tile takes the theme's condensed plot width
