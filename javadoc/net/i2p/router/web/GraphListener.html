      • _coalesceBaseline

        private volatile long _coalesceBaseline
        Coalesce count of the Rate when this listener attached.

        Rate.getCoalesceCount() counts from the Rate's construction, and a stat registered at router startup has been coalescing long before the console attaches to it. Comparing that absolute count against this listener's own write count would report the entire pre-attach history as drift, on every listener, forever. The baseline is what makes the ledger an actual invariant rather than a number that only ever grows.

      • _unrecoverableSteps

        private volatile long _unrecoverableSteps
        Steps proven lost because the Rate no longer retains them.

        The retained-sample ring holds a fixed handful of coalesces, so a listener that was unreachable for longer than that can never recover the intervening steps. Those are reported once rather than retried forever, which needs a counter as well as a flag: "drift is positive" says a step was lost, but only a count says how many are gone for good.

      • noteWrite

        private void noteWrite(long whenSeconds)
        Record a step that is now in the RRD, advancing the write ledger.

        Synchronized because the count is the numerator of the drift invariant the watchdog reads: a lost increment here is reported as a lost step, so the ledger has to be exact rather than a volatile increment that the delivery thread and the watchdog's backfill can race. The monitor covers the field updates only, never the RRD write that precedes them.

        Parameters:
        whenSeconds - archive step written, in seconds

      • noteWriteFailure

        private void noteWriteFailure(Throwable t)
        Count a failed write and report it, without giving up the listener.

        Below the threshold this is routine and rate limited; from the threshold on it is an ERROR naming the rate, because a streak this long is not going to clear itself and the operator has to know which graph is affected. Reported every MAX_CONSECUTIVE_ERRORS failures rather than on every one, so a rate with a persistently failing RRD cannot turn the log into the stall it used to avoid.

        Deliberately does not call stopListening(). Retiring on a transient I/O error left a hole in the graph that nothing refilled for up to a full sync interval, and the detach was indistinguishable from a real fault in the logs. Recording now stops on its own - the ledger drift grows - and the heal ladder reopens or rebuilds the handle when it can.

        Parameters:
        t - the write failure, counted toward the consecutive-error limit

      • backfill

        public int backfill(List<Rate.CoalescedSample> samples)
        Replay retained samples whose steps this listener never stored, oldest first.

        Recovery for a listener that missed a few steps while nothing was obviously wrong: the values are still in the Rate's retained-sample ring, and an archive step is empty forever once nothing writes it, so writing them late beats losing them.

        RrdDb.store rejects any timestamp not strictly newer than the last one stored, so a sample that lands on or before getLastStoredTimeMs() is skipped rather than attempted: the write path has already covered the recent steps and the ring can overlap them.

        Parameters:
        samples - retained samples, oldest first; may be null or empty
        Returns:
        number of steps written

      • toArchiveSecondMs

        static long toArchiveSecondMs(long timestampMs)
        Truncate a wall-clock stamp to the whole second an RRD actually stores.

        Pure because the whole skip rule is this truncation applied against getLastStoredTimeMs(): comparing raw milliseconds would let a sample 999ms into a step the listener already stored look newer than it is, and the write would then be rejected by the archive as non-monotonic.

        Parameters:

      • recoverable

        static boolean recoverable(long lastStoredTimeMs, List<Rate.CoalescedSample> retained)
        Can a listener still recover its drift, or are the missing steps gone?

        The Rate retains a fixed, small ring of coalesces. Once every retained sample is already stored, the steps the listener missed are older than anything the Rate remembers, and no amount of retrying will produce them. Telling those two cases apart is what keeps the watchdog from re-attempting a hopeless backfill every ten seconds and from calling a permanent gap a transient one.

        Pure, so the boundary is unit tested without a Rate, an RRD or a clock.

        Parameters:
        lastStoredTimeMs - newest stored step from getLastStoredTimeMs()
        retained - the Rate's retained samples, oldest first; may be null
        Returns:
        true if at least one retained sample is newer than the last stored step

      • isWritable

        boolean isWritable()
        Whether the open RRD handle can still take a write.

        Distinct from isDetached(): a detached listener has no handle at all, whereas this can be false for a listener that still holds a handle which something else has already closed. That is the cheapest fault to heal, since the listener, its registration and its RRD file all survive and only the handle has to be re-obtained.

        Returns:
        true if the handle is open and can accept a write

      • startListening

        public boolean startListening()
        Open (or re-open) the RRD database and take the Rate's summary registration.

        The ledger baseline is taken before the file is touched, not after: a coalesce that happens while this method is opening the database is a step the listener was never registered for, so it is lost and the drift has to say so. Baselineing afterwards would quietly forgive it.

        Returns:
        true if the database was opened and the summary listener registered

      • reopen

        boolean reopen()
        Re-obtain the RRD handle, keeping this listener registered and its ledger intact.

        The cheapest heal there is, for the case where the handle is closed but the listener itself, its Rate registration and its recorded history all survive. Rebuilding instead would work too, at the cost of a new listener, a new renderer and a window in which the rate has no listener at all - so the ladder tries this first.

        Neither the ledger baseline nor the write count is reset: the drift is the fault being healed, and a heal that quietly rebased it would hide the very loss it is repairing.

        Returns:
        true if a fresh, writable handle is in place

      • openRdd

        private boolean openRdd()
        Build the RRD handle, sample and renderer for this listener.

        Split out of startListening() so reopen() can obtain a new handle without touching the Rate. Does no I/O on any rate's monitor: it is called from the sync task and from the health watchdog, never from a Rate-synchronized callback.

        The three fields are published together, at the end and only on success, so a failure part-way through leaves the listener detached rather than attached with a null sample that the delivery thread would dereference.

        Returns:
        true if _db is set and writable

      • stopListening

        public void stopListening()
        Stop listening and close the RRD database.

        The registration on the Rate is dropped only if this instance still holds it, so tearing down a superseded listener cannot silence its live replacement.

      • closeHandle

        private void closeHandle()
        Release the RRD handle, leaving the Rate registration alone.

        Shared by stopListening() and reopen(): the only difference between tearing a listener down and healing it is whether the Rate keeps pointing at this instance, and that has to be the caller's decision.

        The handle is cleared before it is closed, so a delivery thread that is midway through a write sees a null database and skips rather than writing to a handle that is on its way out.

      • clearRateRegistration

        private void clearRateRegistration()
        Drop our registration on the Rate, but only if we still hold it.

        Rate keeps a single summary listener, so an instance tearing down after a newer one has registered would otherwise stop the newer one being called. The newer one keeps its open RRD and still reports itself attached, so recording dies with no write error, no detach, and no exception anywhere - every health check keeps saying healthy.

        Rate.clearSummaryListener(RateSummaryListener) does the ownership test and the clear as one atomic operation, so a registration that appears between the two cannot be dropped. A clear that finds the registration already gone is the ordinary post-detach case and is not reported; only a registration held by a different live listener is, because that means two teardowns raced.
