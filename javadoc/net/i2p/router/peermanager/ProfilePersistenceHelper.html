      • STALE_PROFILE_AGE_MS

        static final long STALE_PROFILE_AGE_MS
        Age beyond which a peer that is also absent from the network database is treated as gone, making its profile file deletable at any store size.

        Seven days. The previous logic used a 24-hour activity threshold and separately deleted K/L/M/Unknown bandwidth peers regardless of age, so a peer merely quiet overnight could lose its learned history. Those peers are no longer written at all; this threshold now governs only what is left on disk from before that. A peer that has been out of the network for a week will not be selected by a RouterInfo that has since expired anyway.

      • writeProfile

        public boolean writeProfile(PeerProfile profile)
        Write the data from the profile to the file.

        A rare, benign failure mode: a concurrent purge (purgeExcessProfiles(Set, int)) or expiry sweep can remove the profile, or its shard directory (peerProfiles/pX), between pickFile(PeerProfile) and the open. When the shard directory vanished it is re-created and the write retried once so the store stays self-healing; anything else is a race or a genuine store problem and is worth a WARN without a stacktrace, not an ERROR.

        Returns:

      • isGenuinelyStale

        static boolean isGenuinelyStale(boolean absentFromNetDb, long lastActivity, long now, long staleAge)
        Is a profile file genuinely stale, and therefore deletable whatever the store size?

        Both conditions are required. Absence from the network database alone means the RouterInfo expired, which happens routinely while a peer is offline for an hour; inactivity alone means the peer has not been heard from recently, which is equally routine. Only the conjunction identifies a profile whose peer has been gone long enough that its learned history is worth nothing.

        Pure decision, safe for unit tests.

        Parameters:
        absentFromNetDb - true if no usable RouterInfo is held for the peer
        lastActivity - newest of last-sent-successfully, last-heard-from and last-heard-about, or 0 if the profile records none
        now - current time in ms
        staleAge - age beyond which an absent peer is treated as gone, in ms
        Returns:
        true if the file may be deleted regardless of store size

      • surplusToDelete

        static int surplusToDelete(int storedFiles, int retentionFloor, int surplusAvailable)
        How many surplus (non-stale) profiles to delete to bring the store back to the retention floor.

        Stale profiles are deleted independently of this, so this counts only the additional trimming that the store being over its floor justifies. It is zero below the floor, which is what makes "never delete below the floor unless genuinely stale" hold regardless of how many profiles are active.

        Pure decision, safe for unit tests.

        Parameters:
        storedFiles - profile files currently on disk
        retentionFloor - file count to keep, exclusive of stale profiles
        surplusAvailable - surplus profiles not already counted as stale
        Returns:
        number of surplus files to delete, never negative and never more than surplusAvailable

      • purgeExcessProfiles

        public void purgeExcessProfiles(Set<Hash> keepPeers, int retentionFloor)
        Delete profile files that are no longer worth keeping.

        Two rules, in this order:

        1. a profile that is genuinely stale is deleted at any store size, oldest first;
        2. a profile that is merely surplus is deleted only while the store is above retentionFloor, least-recently-active first.
        Staleness therefore decides whether a file may go and the store size decides only how many.

        Low-bandwidth peers are excluded where it belongs, on the write path in PeerManager.storeProfile(), so no K/L/M/Unknown profile is created in the first place. This method used to remove them instead, ahead of any age check, which deleted the file of a peer heard from minutes earlier and only by accident got the right answer: files already on disk from before that check existed still age out here, through the stale bucket or the surplus trim.

        Ordering uses the profile's own recorded activity rather than the file's modification time, because profiles are rewritten whenever they are stored and so carry a fresh mtime even for a peer long gone.

        Parameters:
        keepPeers - peers whose files must be preserved, may be null
        retentionFloor - file count to keep before trimming surplus
