    net.i2p.router.peermanager.RouterInfoRefresher
    class RouterInfoRefresherextends Object
    Per-cycle state for the promotion deferral on a stale RouterInfo.

    Promotion into the fast or high-capacity tier reads whatever RouterInfo the network database currently holds. A RouterInfo older than an hour is likely superseded — routers republish hourly — so promoting on one buys a tier slot that may not survive a build. ProfileOrganizer therefore holds such a promotion back and simply leaves the peer out of the tier; nothing is fetched and no network work is done on the peer's behalf.

    What a cycle needs to remember is therefore only its own bounds and its two counters: the staleness threshold, the tier sizes the starvation guard compares against, how many promotions were held, and how many went ahead on a RouterInfo already known to be stale.

    Locking: confined to the reorganisation write lock, which is also the only caller. Nothing here is written from a job or a selection thread.

      • MISSING_ROUTERINFO_BATCH

        static final int MISSING_ROUTERINFO_BATCH
        Peers looked up per drain when catching up on profiles loaded without a RouterInfo, giving roughly 64 lookups a minute.

        Faster than MAX_ADDRESS_REFRESHES on purpose. That cap is sized for held promotion candidates, a trickle of a few per reorganize; a router coming back from downtime may hold thousands of profiles whose RouterInfo has since expired, and at 16 a minute they would stay unusable for hours. Each lookup is a fire-and-forget lookupRouterInfo, and the netdb negatively caches known-dead keys, so peers that never come back cost little on repeat.

      • _addressRefreshQueue

        private final ArrayDeque<Hash> _addressRefreshQueue
        Peers whose promotion was held for want of a usable address, awaiting a lookup.

        Enqueued from the promotion scan, which runs under the reorganize write lock, and drained after that lock is released, so adds and the poll can overlap across threads. The methods below are therefore synchronized: the critical sections are a single add or a bounded poll, with no network work and no callbacks inside, so the lock is cheap and carries no ordering relationship with the reorganize lock.

      • beginCycle

        boolean beginCycle(long refreshAgeMs, int fastFloor, int highCapFloor)
        Open a cycle, resetting the per-cycle counters.

        There is nothing to stagger here. The earlier startup grace period, quota and queue rotation only ever throttled how many lookups a cycle could issue; with no lookup to issue, each cycle now judges every candidate, and a fresh cycle resets the counters so they report one cycle rather than the life of the router.

        Parameters:

        fastFloor - fast-tier size at or above which a promotion may be held back

      • requestAddressRefresh

        boolean requestAddressRefresh(Hash peer)
        Ask for a RouterInfo lookup for a peer held out of the tiers for want of a usable address.

        A held peer cannot be refreshed directly - that is precisely why it is held, since it has no address to send to - so the only way to re-qualify it is an iterative lookup via other routers. This only records the request; takeAddressRefreshBatch(long) issues it, because the scan that fills this queue runs under the reorganize write lock and must not do network work there.

        Bounded by MAX_ADDRESS_REFRESHES, so a scan over thousands of profiles cannot enqueue thousands of lookups.

        Parameters:
        peer - the held peer
        Returns:
        true if the request was recorded

      • noteMissingRouterInfo

        boolean noteMissingRouterInfo(Hash peer)
        Note that a stored profile was loaded for a peer the netdb cannot resolve.

        Until the RouterInfo comes back the profile is inert: peer selection needs an address to send to, and ProfileOrganizer.isExcludedFromProfiling(Hash) declines to profile a peer with no RouterInfo. The capacity, latency and acceptance history in the file is then retained but unused, which only pays off if something goes and fetches the RouterInfo again.

        Parameters:
        peer - the peer whose profile was loaded
        Returns:
        true if the peer was recorded, false if the set was already full
