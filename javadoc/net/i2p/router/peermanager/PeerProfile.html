    See also main() below for additional commentary.

    Currently, there is no 'ejection' strategy to get rid of the profiles for peers that are no longer active (or when the network consists of thousands of peers, to get rid of peers that are performing poorly). However, the size of each profile is fairly small, and is unrelated to how much data is collected about the peer, so that a router can keep a few thousand active peer profiles before the overhead becomes a serious concern. Once it becomes necessary, we can simply compact the poorly performing profiles (keeping only the most basic data) and maintain hundreds of thousands of profiles in memory. Beyond that size, we can simply eject the peers (e.g. keeping the best 100,000).

    • Field Details

      • LOSS_DECAY_HALF_LIFE_MS

        static final long LOSS_DECAY_HALF_LIFE_MS
        Half-life of the decayed loss score: with no new transport report the score halves every 15 minutes, continuously. Chosen so a transient congestion episode (a 25-40% retransmit ratio) falls back under the 0.20 lossy threshold in roughly 20-40 minutes instead of the hour-plus an hourly-quantized decay imposed, while a peer that keeps reporting loss stays gated. Each report re-inflates the score through the max() fold in setLossRatio(float, long).

      • FIRST_HOP_RTT_VALIDITY_MS

        static final long FIRST_HOP_RTT_VALIDITY_MS
        How long a recorded first-hop RTT stays usable.

        Four hours rather than the RateConstants.ONE_HOUR Active tier period that getLastSendSuccessful() uses. Link latency is a slow-changing property of a path, and it is now refreshed continuously by ProfileOrganizer.sampleFirstHopRtts() on every reorganize, so this window no longer decides how current a measurement is -- it only decides how long a value outlives the session that produced it. An hour threw away measurements of peers we simply had not talked to lately, which is what left the profiles page 97% blank.

        The cost is that a peer whose session has gone away keeps its latency standing for up to four hours, and the low-latency bar is absolute, so a stale value is trusted as though current. If peer counts or the fast-tier mix look wrong after this, this constant is the first thing to lower.

      • LOW_LATENCY_FLOOR_MS

        static final long LOW_LATENCY_FLOOR_MS
        Absolute floor for the low-latency flag, in ms. This is the binding criterion: a peer counts as low latency only if its direct-link RTT is at or below this value.

        This replaced a 0.5 * mean relative test. The relative form was unsound for two reasons. First, the population it divided came from a decaying, self-selecting sample: an RTT is valid for one hour and refreshes only when we happen to send to that peer, so on a ~950 peer fast tier only ~37% carried a usable value and the mean tracked whoever we most recently happened to contact. A mean drawn from that set shrinks as it shrinks, so halving it ratchets the bar tighter over time. Second, the arithmetic did not discriminate. Measured against a live fast tier the mean was 86ms, so the bar sat at 43ms — below the population's own median of 60ms, which demoted two thirds of every measured peer rather than a tail.

        A fixed 100ms admits 69% and evicts 31% on that same population, which is the discrimination the flag was meant to provide. It also does not move as the sample decays, which was the defect that made the relative form unsafe to leave in place.

      • dampLatency

        static float dampLatency(float current, float sample)
        The one smoothing applied to every latency measurement, whatever measured it.

        Peer latency reaches the profile from three directions — a peer test's whole-tunnel round trip, the direct-link RTT a transport has measured for a live session, and an SSU/NTCP handshake. They are different quantities, but they are averaged the same way so that any one of them can be compared with any other: a value damped 25% per sample behaves the same whether the sample came from a tunnel round trip or a handshake.

        An unknown or zero current value is replaced rather than averaged. A measurement is evidence; the absence of one is not, and damping toward zero would manufacture latency out of missing data.

        Parameters:
        current - the stored average in ms, or 0/negative when unknown
        sample - the new measurement in ms
        Returns:
        the new average in ms

      • setFirstHopRtt

        public void setFirstHopRtt(int rtt, long when)
        Record the transport's measured round trip time to this peer.

        This is the direct link cost, which is what first-hop selection needs. A value of 0 means the session has not measured yet and is stored as unknown rather than as zero latency.

        Damped through dampLatency(float, float), the same smoothing the peer-test average uses, so a single session's noisy sample cannot set the value on its own. A value that has already gone stale is replaced rather than damped: getFirstHopRtt(long) has declared it unknown, so averaging toward it would let expired evidence drag a fresh measurement back.

        A sample older than the one already held is discarded outright. This is the single choke point every measurement passes through - the sampling pass, the pre-connect probe and the handshake recorder all land here - so the rule cannot be bypassed by a caller that forgot it. Without it a transport whose reading is old but not yet expired re-submits that same old number each cycle, which both drags the average back toward one stale sample and pushes the timestamp forward, so the staleness window never opens.

        Parameters:
        rtt - measured round trip time in ms, 0 if unmeasured
        when - timestamp of the measurement; must not predate the value held

      • getLowLatencyForFirstHopRtt

        public Boolean getLowLatencyForFirstHopRtt(long now, long ceilingMs)
        Whether this peer counts as low latency, judged on its direct link.

        The single low-latency decision: recalculateLowLatency() is a thin wrapper over this, so the flag is derived one way everywhere. Two implementations of the same comparison is how the flag ends up disagreeing with itself depending on which pass happened to run last.

        Two drivers, both required, because either alone is misleading:

        • an absolute ceiling, so a peer is never low latency merely because the whole network has slowed and every average rose with it;
        • an absolute floor, so on a fast network a peer at the absolute ceiling is still not low if it sits at the typical value.

        Only the direct link is consulted. Latency to this peer has nothing to do with how long a build or test involving other peers took.

        Parameters:
        now - current time in ms
        ceilingMs - absolute low-latency ceiling in ms
        Returns:
        TRUE or FALSE, or null when this peer has no usable first-hop RTT

      • recalculateLowLatency

        void recalculateLowLatency()
        Recalculate the low-latency flag from the measured direct-link RTT.

        The only low-latency decision in the codebase: both callers. The reorganize sampling pass and the recorder that runs when a measurement arrives — come through here, so the flag cannot be derived two different ways from the same field.

        Judged on the direct link to this peer, not on how long a test through a multi-hop tunnel took. getPeerTestTimeAverage() is the round trip across every hop of that tunnel, so using it here measured the latency of hops the peer was merely a member of.

        An unmeasured peer keeps whatever was persisted: absent evidence is not evidence of high latency.

      • recalculateLowLatency

        void recalculateLowLatency(Long calibratedFloorMs)
        Recompute the low-latency flag, optionally against a calibrated per-transport floor instead of the absolute one.

        This remains the single low-latency decision. The calibrated floor only supplies an alternative bar and never a separate verdict. It is deliberately one-directional: the floor is derived from measured link latencies across all peers, and nothing about this peer's tier membership feeds back into it, so no cycle can tighten the bar in response to the tiers that bar itself produces.

        A null or negative calibratedFloorMs means the transport has no calibrated opinion yet, and the absolute rule applies unchanged - so on a cold router the behaviour here is identical to it being absent.

        Parameters:
        calibratedFloorMs - the transport's calibrated floor in ms, or -1/null when unknown

      • recalculateLowLatency

        void recalculateLowLatency(Long calibratedFloorMs, Long cohortFloorMs)
        Recompute the low-latency flag against the calibrated bounds.

        This remains the single low-latency decision. The calibrated values only supply alternative bars and never a separate verdict. It is deliberately one-directional: the floors are derived from measured link latencies across all peers, and nothing about this peer's tier membership feeds back into them, so no cycle can tighten a bar in response to the tiers that bar itself produces.

        A null or negative value means that bound has no calibrated opinion yet and is skipped, leaving the absolute rule to decide alone. On a cold router both are null, so behaviour is identical to their absence.

        Both calibrated bounds can only ever widen the absolute rule, never narrow it: the Organizer clamps the transport floor to at least LOW_LATENCY_FLOOR_MS / multiple, and the cohort floor is applied only where the absolute rule already agreed.

        Parameters:
        calibratedFloorMs - the transport's calibrated floor in ms, or null
        cohortFloorMs - the fast-cohort floor in ms, or null
