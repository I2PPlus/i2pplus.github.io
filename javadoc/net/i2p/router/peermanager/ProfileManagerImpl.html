      • messageSent

        public void messageSent(Hash peer, String transport, long msToSend, long bytesSent)
        Note that it took msToSend to send a message of size bytesSent to the peer over the transport. This should only be called if the transport considered the send successful. Non-blocking. Will not update the profile if we can't get the lock.

        This runs per message, so the cost is one getOrCreateProfileNonblocking — a tryReadLock() plus a map probe — and, on the rare miss, one tryWriteLock() to insert the newly created profile. Both are non-blocking, so neither can stall the transport thread behind reorganize; see peerLossEvent(Hash, float) for why the write-lock attempt is not a contention hazard. Left unchanged deliberately: the profile must exist for setLastSendSuccessful to be recorded at all, so a non-creating variant would silently drop first-contact send-success timestamps.

        Specified by:
        messageSent in interface ProfileManager
        Parameters:
        peer - hash of the peer the message was sent to
        transport - style of the transport that carried the message
        msToSend - milliseconds the send took
        bytesSent - size of the message in bytes

      • peerLossEvent

        public void peerLossEvent(Hash peer, float ratio)
        Record the packet-loss (retransmit) ratio measured by the transport for a peer. Non-blocking. Will not update the profile if we can't get the lock.

        Note on the write lock below: ProfileOrganizer.demoteIfLossy(Hash) does attempt the reorganize write lock, but it uses tryWriteLock(), which returns immediately rather than waiting, and the caller is already committed to the non-blocking contract of this method — so the message path cannot be stalled by reorganize. Frequency is also bounded well below message rate: PeerState.reportLossRatio only calls this when the retransmit ratio crosses a 5% bucket after at least ProfileOrganizer.PROP_LOSSY_MIN_PACKETS packets, so the write-lock attempt happens at most once per bucket per connection, not per packet. The check is left in place deliberately: dropping it would leave a lossy peer in the fast/high-cap tiers until the next reorganize judged it.

        Specified by:
        peerLossEvent in interface ProfileManager
        Parameters:
        peer - hash of the peer the loss was measured on
        ratio - retransmitted / transmitted packets, 0.0 = healthy

      • updateFloodfillReliability

        void updateFloodfillReliability(PeerProfile data)
        Compute floodfill reliability from DBHistory. Updates the peer's reliability classification based on successful/failed lookup and store counts.

        Thresholds: - UNKNOWN: 0 successful lookups (probing target) - OK: 1-4 successful lookups with >=50% success rate - GOOD: >=5 successful lookups with >=80% success rate - BAD: >=5 total lookups with <50% success rate.

      • messageReceived

        public void messageReceived(Hash peer, String style, long msToReceive, int bytesRead)
        Note that the router received a message from the given peer on the specified transport. Messages received without any "from" information aren't recorded through this metric. If msToReceive is negative, there was no timing information available. Non-blocking. Will not update the profile if we can't get the lock.

        Same per-message cost profile as messageSent(Hash, String, long, long), and the same decision to leave it alone: one tryReadLock() plus a map probe on the hot path, with no lock escalation that could block the caller.

        Specified by:
        messageReceived in interface ProfileManager
        Parameters:
        peer - hash of the peer that sent the message
        style - transport style the message arrived over
        msToReceive - milliseconds the receive took, negative if untimed
        bytesRead - size of the message in bytes
