    Per-cycle tally of why keepalive did not act on the peers it selected.

    Added because the candidate pool was observed shrinking from roughly 395 peers per cycle to roughly 203, and the pre-existing log line only reported how many peers were kept alive, never how many were dropped on the way. Without a reason for each drop, an eroding pool and a busy pool look identical from the outside.

    Note that the fall from 395 to 203 is supply, not delivery: the action budget sits at 200, so the cycle was servicing its full budget in both periods and only the surplus above it collapsed.

    describe(boolean) is pure so the summary can be asserted in a test without a router.

    • Field Details

      • budget

        int budget
        Peers the selector asked for, before any filtering.

        This is the per-tier request doubled for the two tiers, not a count of anything on the wire.

      • candidates

        int candidates
        Distinct peers the two tier selectors returned.

        Named candidates rather than delivered because it is fixed before the cycle sends anything: it measures supply, not delivery. A previous field name of delivered sat on this same value and read as "203 delivered of 400 requested", which was mistaken twice for a fall in successful keepalives when it only ever showed the candidate pool.

        May exceed budget, which is the sum of the two nominal tier requests rather than a cap. selectFastPeers backfills from the high-capacity tier when the fast tier cannot fill its depth, and each selector adds up to its own depth to whatever the set already holds.
