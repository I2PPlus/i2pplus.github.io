    Runnable
    public class BuildExecutorextends Object implements Runnable
    Single threaded controller of the tunnel creation process, spanning all tunnel pools. Essentially, this loops across the pools, sees which want to build tunnels, and fires off the necessary activities if the load allows. If nothing wants to build any tunnels, it waits for a short period before looping again (or until it is told that something changed, such as a tunnel failed, new client started up, or tunnel creation was aborted).

    Note that the default 11 minute tunnel expiration is assumed in here.

    As of 0.8.11, inbound request handling is done in a separate thread.

    • Field Details

      • DISPATCH_COMPARATOR

        static final Comparator<Object[]> DISPATCH_COMPARATOR
        Dispatch comparator for snapshotted Object[3] rows where row[0] is the score (Integer), row[1] the pool and row[2] the zero-hop emergency flag (Boolean): emergency replacements go first regardless of deficit, then higher score first. Deliberately no identity-hash tiebreaker — Arrays.sort is stable, so full ties keep their allocation order from calculatePairedBuilds() instead of an arbitrary per-session order that could starve one of two equally-ranked pools indefinitely.

      • SLOW_BUILD_MS

        static final long SLOW_BUILD_MS
        Build completion time above which a build counts as slow.

        Half the floor the build reply deadline is clamped to in calculateAdaptiveTimeoutFromSuccess(). Half rather than the deadline itself, so the count stays selective: anything it records is a build that would have been at risk of expiring had the budget been at its floor. If nearly every build were counted the stat would just mirror tunnel.buildClientSuccess and say nothing new, and if none were it would be dead.

        This exists for the same reason as udp.*EstablishSlow. The success stats record a duration but expose only a mean, and build latency is right-skewed, so the mean says little about the builds that nearly timed out - which are exactly the ones a reply budget has to cover.

      • elevateForUrgent

        static int elevateForUrgent(int base, int urgent, int inProgress)
        Elevated ceiling when urgent demand cannot be served at the current one. Pure, so the rule is testable without a router.

        Elevates only for the urgent pool's own build plus headroom, bounded by the ceiling's own maximum, and only when there is not already room under it. An ordinary deficit does not elevate: that demand is served a pool per cycle in score order, which is what keeps a busy router from permanently raising its ceiling to service pools that are merely below target.

        Parameters:
        base - the ceiling now in force
        urgent - pools holding leases about to expire
        inProgress - builds already in flight
        Returns:
        the ceiling to use, which may equal base

      • score

        static int score(int active, int target, int pairedActive, int nearExpiry)
        Pure form of the dispatch score, so the ordering can be pinned without building pools.

        Tiers, highest first:

        1. collapsed (no usable tunnel) — a pool with no service at all;
        2. near-collapse (1-2 usable);
        3. leases about to expire;
        4. deficit against target;
        5. paired balance — the direction behind its pair.

        Expiry sits above deficit and below near-collapse deliberately. A pool holding fewer tunnels than target but with hours on its leases can wait a cycle; a pool whose leases lapse in the pre-build window is losing its service in minutes and the replacement needs that same window to build. It stays below near-collapse so a genuinely thin pool is never starved by a merely time-urgent one.

        The expiry bonus is capped at MAX_EXPIRY_BONUS tunnels, so a pool that keeps producing near-expiry tunnels cannot accumulate unbounded priority — the urgency is consumed when the lease lapses.

        Parameters:
        active - usable tunnels in the pool
        target - the pool's target quantity, already floored at 2
        pairedActive - usable tunnels in the paired pool, for balance
        nearExpiry - live tunnels inside the pre-build window
        Returns:
        the score, higher builds sooner

      • adaptiveTimeoutDelta

        static long adaptiveTimeoutDelta(double successRate)
        The adjustment to add to the base build timeout, from the success rate alone.

        The timeout rate is deliberately not an input. It used to be, and reaching that branch was itself a bug worth recording: the test sat after successRate > 0.50, so the intended +7s was unreachable for every success rate above half - exactly the band where a high timeout rate is most expensive, a timeout burning a whole build slot where a reject costs a round trip. Reordering fixed the reachability and the +7s then did what it said.

        It no longer belongs here. The +7s was justified while an outbound session establishment was abandoning ~117 handshakes a minute at 2250ms: a build waiting on one of those genuinely needed more time. That deadline is now floored at 4000ms and the abandonments are gone, so the timeouts that remain are not premature ones, and buying them 7 extra seconds only holds a build slot longer. Measured across an 11.8 minute window either side of that change, build success fell from 64.5% to 56.0% (-8.5pp, 4.2 sigma) and throughput 12%, with the timeout-to-reject ratio worsening from 1.55:1 to 3.2:1 - the signature of builds waiting rather than failing.

        The timeout rate still drives the concurrency throttle below, which is the lever that reduces occupancy. One signal, one lever: timeouts should shrink the amount of work in flight, not inflate how long each item may hold a slot.

        Parameters:
        successRate - fraction of recent builds that succeeded, 0..1
        Returns:
        milliseconds to add to the base timeout; may be negative

        static long combineAdaptiveTimeout(long baseTimeout, double successRate)
        Combine the Tuner's base timeout with the success-rate adjustment.

        Pure, and deliberately unclamped. The base is already bounded by the Tuner's own range, and the final budget is bounded by computeAdaptiveTimeout(long, int, boolean, int, long) through MAX_ADAPTIVE_TIMEOUT_MS, so clamping here to the same endpoints as the base only destroyed information: with the base at 30s the GOOD (+0), MODERATE (+2s) and LOW (+5s) branches all collapsed onto 30s, and with the base at 10s the FAST (-3s) branch collapsed up to 10s. Logged samples sat pinned at the 30s ceiling 75% of the time, which is what a degenerate ladder looks like from outside.

        Extracted from the adaptive-timeout update so that reachability of every branch across the base range is unit-testable without a router. While the arithmetic lived only inside the instance method, the sole way to test it was to reimplement it in the test -- which passes whether or not the real code clamps, so it proved nothing.

        baseTimeout - the Tuner's current build request timeout in ms
        successRate - fraction of recent builds that succeeded, 0..1
        Returns:
        the base adjusted for success rate, in ms; not clamped

      • penalizeTimeout

        void penalizeTimeout(PooledTunnelCreatorConfig cfg)
        Penalize the peers of an expired build. Only the hop the build request was dispatched to — the gateway (peer 0) for inbound, the next hop (peer 1) for outbound, per BuildRequestor.getBuildRequestPeer(PooledTunnelCreatorConfig) — failed to deliver a reply; the other hops may never have received the request, or may be waiting downstream of a silent peer. Blaming them all shrinks the pool on innocent peers during network-wide no-reply events, so the profile penalty and ghost mark go to the contacted hop only. The per-tier expire stat and the didNotReply debug log stay per-hop for accounting and triage.

        Every non-self hop is additionally cooled down out of the immediate retry selection (cooldownFailedPeers(PooledTunnelCreatorConfig)), since any of them may have been the silent one.

        Parameters:
        cfg - the expired build config, non-null

      • shouldChargeGhostMark

        boolean shouldChargeGhostMark(PooledTunnelCreatorConfig cfg, Hash contacted)
        Whether an expired build's contacted hop should be charged a ghost mark.

        A ghost mark is a peer exclusion, so it should rest on evidence that indicts the peer. When the contacted hop is established but silent it is not: the hop accepted the connection, so the peer was reachable, and the missing reply is equally consistent with the request being dropped inside the peer, the reply being lost on the return path, or our own path being the problem. Charging that case excludes peers for a fault they may not own.

        It is also the dominant bucket. On a live router under stress the contacted-hop expiries split roughly 27.7/min established-silent against 4.3/min unreachable and 4.7/min merely reachable, so this single decision governed the majority of all ghost marks taken. Suppressing it stops the exclusion set growing faster than ghostMarksCleared can retire it — the observed 82/min in against 15/min out — which was steadily shrinking the pool selection draws from.

        Every other classification still charges: unreachable, handshake unfinished and plain reachable all leave the peer as the best available explanation for the expiry. The selection-scope cooldown from cooldownFailedPeers(PooledTunnelCreatorConfig) still applies either way, so an ambiguous peer is still not retried immediately.

        Parameters:
        cfg - the expired build config
        contacted - the hop the request was dispatched to
        Returns:
        true if the contacted hop should be charged a ghost mark

      • buildTunnel

        void buildTunnel(PooledTunnelCreatorConfig cfg)
        Build a tunnel with the given configuration. Burst builds to different peers freely, but never start a second build request to a first-hop peer that already has a build in flight — stacking requests on one peer floods it and makes the first build answer slower.       • countExpiryBuckets

        static BuildExecutor.ExpiryBuckets countExpiryBuckets(List<TunnelInfo> tunnels, long now)
        Count a pool's tunnels into cumulative expiry-window buckets. Tunnels at or below one window boundary fall into that window (and no later one), so expire30s is "expires within 30s", expire90s is "within 90s but not 30s", and so on. ExpireLater covers everything beyond 330s. Each bucket has a GOOD-only twin (good status and at most 1 consecutive failure) used for proactive replacement, plus aggregates: zero-hop fallback count, GOOD count and their total latency.

        Length-1 tunnels always land in fallbackCount and never fill the expiry buckets, so pools that don't explicitly request zero-hop tunnels keep building replacements until the fallback is gone.

        now - current time, used to compute time-to-expiry
        Returns:
        bucket counts, never null
