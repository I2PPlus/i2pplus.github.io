    Runnable
    public class BuildExecutorextends Object implements Runnable
    Single threaded controller of the tunnel creation process, spanning all tunnel pools. Essentially, this loops across the pools, sees which want to build tunnels, and fires off the necessary activities if the load allows. If nothing wants to build any tunnels, it waits for a short period before looping again (or until it is told that something changed, such as a tunnel failed, new client started up, or tunnel creation was aborted).

    Note that the default 11 minute tunnel expiration is assumed in here.

    As of 0.8.11, inbound request handling is done in a separate thread.

      • score

        static int score(int active, int target, int pairedActive, int nearExpiry)
        Pure form of the dispatch score, so the ordering can be pinned without building pools.

        Tiers, highest first:

        1. collapsed (no usable tunnel) — a pool with no service at all;
        2. near-collapse (1-2 usable);
        3. leases about to expire;
        4. deficit against target;
        5. paired balance — the direction behind its pair.

        Expiry sits above deficit and below near-collapse deliberately. A pool holding fewer tunnels than target but with hours on its leases can wait a cycle; a pool whose leases lapse in the pre-build window is losing its service in minutes and the replacement needs that same window to build. It stays below near-collapse so a genuinely thin pool is never starved by a merely time-urgent one.

        The expiry bonus is capped at MAX_EXPIRY_BONUS tunnels, so a pool that keeps producing near-expiry tunnels cannot accumulate unbounded priority — the urgency is consumed when the lease lapses.

        Parameters:
        active - usable tunnels in the pool
        target - the pool's target quantity, already floored at 2
        pairedActive - usable tunnels in the paired pool, for balance
        nearExpiry - live tunnels inside the pre-build window
        Returns:
        the score, higher builds sooner

      • adaptiveTimeoutDelta

        static long adaptiveTimeoutDelta(double successRate)
        The adjustment to add to the base build timeout, from the success rate alone.

        The timeout rate is deliberately not an input. It used to be, and reaching that branch was itself a bug worth recording: the test sat after successRate > 0.50, so the intended +7s was unreachable for every success rate above half - exactly the band where a high timeout rate is most expensive, a timeout burning a whole build slot where a reject costs a round trip. Reordering fixed the reachability and the +7s then did what it said.

        It no longer belongs here. The +7s was justified while an outbound session establishment was abandoning ~117 handshakes a minute at 2250ms: a build waiting on one of those genuinely needed more time. That deadline is now floored at 4000ms and the abandonments are gone, so the timeouts that remain are not premature ones, and buying them 7 extra seconds only holds a build slot longer. Measured across an 11.8 minute window either side of that change, build success fell from 64.5% to 56.0% (-8.5pp, 4.2 sigma) and throughput 12%, with the timeout-to-reject ratio worsening from 1.55:1 to 3.2:1 - the signature of builds waiting rather than failing.

        The timeout rate still drives the concurrency throttle below, which is the lever that reduces occupancy. One signal, one lever: timeouts should shrink the amount of work in flight, not inflate how long each item may hold a slot.

        Parameters:
        successRate - fraction of recent builds that succeeded, 0..1
        Returns:
        milliseconds to add to the base timeout; may be negative

        A ghost mark is a peer exclusion, so it should rest on evidence that indicts the peer.       • countExpiryBuckets

        Count a pool's tunnels into cumulative expiry-window buckets.
