      • MAX_NEXT_HOP_LOOKUP_RETRIES

        static final int MAX_NEXT_HOP_LOOKUP_RETRIES
        Extra RI lookup attempts allowed after a next-hop lookup times out. A timeout here is a local netdb miss (floodfills slow, RI just evicted), not evidence the peer is bad — rejecting threw away builds the next attempt would have completed. One retry keeps the total inside the originator's request budget (BuildRequestor.getRequestTimeout(RouterContext), gated by shouldRetryLookup(int, long, long, int, int)).

      • BAN_INFLIGHT_THRESHOLD_MS

        static final long BAN_INFLIGHT_THRESHOLD_MS
        Age below which a ban is treated as having landed during the build.

        A tunnel build takes tens of seconds, so a ban recorded seconds ago cannot have been visible to the peer selector that dispatched this request. Longer than that, the ban predates the request and selection handed out a peer the banlist already held.

      • lookupLimit

        static int lookupLimit(int numTunnels, int minLimit, int maxLimit, int percentLimit, long uptimeMs)
        Concurrent next-hop lookup limit for the current request.

        Within STARTUP_LOOKUP_BOOST_MS of startup the full ceiling applies regardless of participating count: the netDb is still filling, so cache misses dominate and the proportional formula would clamp concurrency to near its floor exactly when inbound builds queue up. Afterward, scale with transit population as before, floored at minLimit so a drained pool can't zero out lookups.

        Pure decision — safe for unit tests.

        Parameters:
        numTunnels - current participating (transit) tunnel count
        minLimit - configured floor for the proportional formula
        maxLimit - configured ceiling for the proportional formula
        percentLimit - percent of participating count usable as slots
        uptimeMs - router uptime in ms
        Returns:
        the concurrent lookup limit, never below minLimit

      • attachLookupKey

        static boolean attachLookupKey(ConcurrentHashMap<Hash, AtomicInteger> inFlight, Hash key, int limit)
        Attach a build request's next hop to the in-flight lookup set. Capacity counts DISTINCT keys: requests joining an already-attached key consume no extra slot, because the netdb coalesces duplicate lookups for one key into a single network round trip. Without this, N builds missing the same popular hop would burn N slots to run one search and starve unrelated keys.

        The limit is soft: racing handler threads may transiently overshoot by at most the thread count, which is harmless.

        Pure decision on its map argument — safe for unit tests.

        Parameters:
        inFlight - distinct next-hop keys currently being resolved
        key - next hop of this request
        limit - concurrent distinct-key ceiling
        Returns:
        true if attached and a lookup should be issued; false when the ceiling is reached and the request must queue

        static boolean shouldRetryLookup(int retriesLeft, long lookupStartedMs, long nowMs, int lookupTimeoutMs, int requestTimeoutMs)
        Whether a timed-out next-hop lookup deserves one more attempt. Retry only when a full extra lookup still fits inside the originator's build-request budget. Past that, the originator has given up and completing the join is wasted work (same reasoning as pendingLookupMaxAge(long, long)).
        Parameters:

        lookupStartedMs - wall-clock time the first lookup started, 0 if unknown
        nowMs - current wall-clock time
        lookupTimeoutMs - per-lookup timeout (ms)
        requestTimeoutMs - originator's build request timeout (ms)
        Returns:
        true when another full attempt fits in the remaining budget

      • pendingLookupMaxAge

        How long a queued next-hop lookup may wait before it is discarded as stale.       • banSeverity

        static String banSeverity(long banAgeMs)
        Classify why a next-hop peer is banlisted, for the rejection log.

        Pure and static so the classification is testable without a banlist. Keyed on how long the banlist has held the peer (Banlist.getBanAge), not on the ban's duration class: a peer permanently banned mid-flight and one banned last week both report as "permanent", so the duration class cannot distinguish the case that points at peer selection from the case that points at a selection-time cooldown.

        Parameters:
        banAgeMs - age of the standing ban, ms; negative when unknown
        Returns:
        a short label for the log line, never null

      • countNextHopOutcome

        static boolean countNextHopOutcome(int outcome, Log log, long now)
        Count one next-hop outcome and, at most once per NEXT_HOP_SUMMARY_INTERVAL_MS, log the ratio at WARN.

        This exists because the failure was invisible: 42% of handled inbound builds hit the hop-contact timeout, but the only record was one DEBUG line per event, so an eepsite silently stopped serving and nothing at WARN reflected it. The rate is the diagnostic signal, not any single event — one slow peer is noise, a sustained third of builds unanswered is a reachability problem.

        Parameters:
        outcome - one of NEXT_HOP_REPLIED, NEXT_HOP_TIMEOUT, NEXT_HOP_DROPPED
        log - the log to write to, may be null
        now - current time in ms
        Returns:
        true if a summary was logged
