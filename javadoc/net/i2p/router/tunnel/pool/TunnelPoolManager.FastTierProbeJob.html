    Background reachability probe over the peers a client pool would provisionally use as a first hop.

    Selection samples a bounded slice of the high-capacity tier (ProfileOrganizer.maxCandidateSample(int, int)), so an unconnectable peer can sit in that tier indefinitely and be drawn into builds that fail at the first hop. Nothing else records reachability cheaply: send-failure strikes only accumulate on tunnels already in use, and a peer that never answers produces no reply to blame. This job supplies that missing signal by pre-connecting to a bounded slice and letting TunnelPeerSelector.PreConnectFailJob demote whatever fails.

    Sweep, pause, sweep: each pass probes at most PROBE_BATCH peers and then waits PROBE_INTERVAL, so the whole tier is covered over several passes without a burst of outbound traffic. Only peers we are not already talking to are probed — a peer with recent successful traffic has fresh evidence already, and probing it would spend the budget re-confirming what we know.

      • RECENTLY_ACTIVE_MS

        static final long RECENTLY_ACTIVE_MS
        A peer we have built through this recently needs no probe.

        Deliberately generous, and comfortably wider than one build cycle: a peer we are already successfully sending through is confirmed for as long as that keeps being true, so the only peers worth spending budget on are the idle ones the sweep exists to find. A narrow window would re-probe the peers working hardest, which is where the budget is least useful.

        Widening this constant reduces coverage. It widens the skip set, not the probe set — so it is only safe because the test below keys on our own send successes rather than on incidental inbound traffic.

      • FAST_PASS_TARGET_MS

        static final long FAST_PASS_TARGET_MS
        Wall clock wanted for one pass over the whole tier, while young.

        A young router has measured nothing, so the tier is unpopulated with first-hop latency and nothing can be judged until it is covered. Twenty minutes reaches a full sweep quickly without turning the probe into a sustained flood: probes carry establishment cost and the failures that come with it, and those failures are what demote peers.

      • probeIntervalFor

        static long probeIntervalFor(long uptimeMs, int bandSize, int batch)
        Gap between passes, derived from the tier size so a full sweep takes a predictable wall-clock time whatever the population.

        Computing the interval from targetPass * batch / bandSize rather than fixing it means the same cadence holds at 200 peers or 2000: a small tier is not over-probed and a large one is not starved. Clamped so a very small or very large band cannot produce an absurd interval.

        Parameters:

        bandSize - how many peers are selectable, non-negative
        batch - peers per pass, must be positive
        Returns:

      • isRecentlyActive

        static boolean isRecentlyActive(RouterContext ctx, Hash peer, long now)
        Whether this peer has traffic recent enough that probing adds nothing.

        Only our own successful sends count. Inbound hearing is deliberately ignored: PeerProfile.getLastHeardFrom() advances on DHT replies, explore traffic and transit acknowledgments, so it marks most of the tier as recently active without ever showing the peer works as a first hop. Keying on it made a 2 minute window behave like a much longer one and left a pass probing 33 peers out of a 128 budget.

        Parameters:
        ctx - the router context
        peer - the peer to test
        now - current time in ms
        Returns:
        true if recent traffic means we should skip probing
