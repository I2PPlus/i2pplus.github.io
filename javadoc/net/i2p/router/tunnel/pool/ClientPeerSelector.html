    • Field Details

      • WIDEN_BUILD_SUCCESS

        static final double WIDEN_BUILD_SUCCESS
        Build success below which the first hop draws on both the Fast and HighCapacity tiers.

        The two tiers hold different peers: Fast is speed-ranked, HighCapacity is proven-reliability. Below this the network is not delivering often enough for the distinction to earn its cost, and taking from only one of them needlessly halves the pool.

        See Also:
        • Constant Field Values

      • WIDEN_FAST_PEERS

        static final int WIDEN_FAST_PEERS
        Fast-tier size below which the first hop draws on both tiers regardless of build success.

        A small Fast tier cannot supply FIRST_HOP_CANDIDATES candidates however healthy the network looks, so the batch is worth completing from the other tier even when success is high. The same 300 marks the point where cross-pool diversity engages, so both decisions agree on what counts as a large enough Fast tier.

      • CONNECTING_PREF_BUILD_SUCCESS

        static final double CONNECTING_PREF_BUILD_SUCCESS
        Build success below which the first-hop quality loop starts one tier lower, accepting peers with only a connecting transport session rather than requiring an established one.

        Distinct from WIDEN_BUILD_SUCCESS: this widens the transport requirement, which costs build latency, so it waits until success is closer to healthy.

        static final double CROSS_POOL_BUILD_SUCCESS_MIN
        Cross-pool diversity is only active when build success is above this threshold. Higher than TunnelPeerSelector.ATTACK_THRESHOLD because cross-pool exclusion is far more aggressive (excludes ALL active peers across ALL pools) and can starve builds when most fast peers are in active tunnels.

        static final double CROSS_POOL_EXCLUSION_RATIO
        Cross-pool exclusion may not consume more than this fraction of the fast tier. When most fast peers are in active tunnels, natural pool-local diversity already provides enough variability — explicit exclusion risks starvation.

      • selectPeers

        public List<Hash> selectPeers(TunnelPoolSettings settings, Set<Hash> excludeFirstHops)
        Select peers for a new tunnel, excluding given peers from first-hop selection. Used by the build executor's dispatch loop to ensure concurrent builds in the same batch target diverse first-hop peers — stacking multiple build requests on one peer floods it and makes the first build answer slower.

      • shouldDiscardShortSelection

        static boolean shouldDiscardShortSelection(int rvSize, int min)
        Whether a post-finalize selection is too short to build and must be discarded for a redraw.

        Pure decision helper for the shortfall guard in selectPeers(), extracted for unit testing. A selection is discarded only when it holds fewer than MIN_STRUCTURAL_NON_SELF_HOPS non-self hops — that is, when it cannot form a tunnel regardless of what was requested. Anything longer is returned as a short tunnel, which the shortfall ladder already produces deliberately; discarding those to force a redraw converts a one-hop shortfall into a whole lost build cycle, and at minimum length (what a starved pool asks for) there is no slack to absorb it.

      • shouldPreConnect

        static boolean shouldPreConnect(RouterContext ctx, Hash peer)
        Determines whether preConnectTo() should be called for a first-hop candidate. Returns false (skip pre-connect) when the build timeout is sufficient to survive the ~8.5s SSU2 handshake, the peer was recently connected, or the feature is disabled. Returns true when pre-connect is needed to ensure reliable tunnel delivery.

        Approach 1: If the request timeout exceeds 15s, the message survives the handshake, so skip pre-connect. Approach 3: Property toggle allows runtime disabling. Approach 4: Recently connected peers don't need pre-connect again.

        The timeout is read through BuildRequestor.getRequestTimeout(RouterContext) so it reflects the budget the builder actually runs with, including runtime tuning. Reading ctx.getProperty here instead saw neither the tuned value nor a configured one: with the property unset its own default equalled the threshold, so the comparison was always true and first-hop pre-connect never ran on a default install.

        Pure decision — no side effects.

        Parameters:
        ctx - the router context
        peer - the first-hop candidate
        Returns:
        whether preConnectTo() should be called for this peer
