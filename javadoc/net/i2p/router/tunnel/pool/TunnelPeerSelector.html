        protected static final int FAILURE_MAP_MAX_SIZE
        Size bound for the cooldown maps (_peerCooldowns, _firstHopFails, ExploratoryPeerSelector._exploratoryCooldowns). Entries are recorded on selection failures, tunnel rejects, and tunnel reuse. They expire lazily (read-time filtering during selection) and are bulk-pruned only when a map exceeds this bound, so these maps stay small — 128 entries is already generous. This bound only limits growth between selections; it does not evict live entries.

      • ATTACK_RELAX_EXIT

        static final double ATTACK_RELAX_EXIT
        Whether the exclude caps are currently relaxed, and by how much build success has to recover before they are enforced again.

        Wider than ATTACK_THRESHOLD on purpose: relaxing the caps widens the peer pool, which raises build success, which would otherwise release the relaxation immediately and put the caps back — a loop that ratchets the peer pool between wide and narrow several times a minute. The gap is what lets the widening actually take hold.

      • SCARCE_FAST_PEERS

        public static final int SCARCE_FAST_PEERS
        Number of fast peers at or above which the peer set is considered well supplied and the activity window is never widened on availability grounds.

        Deliberately far below the ~1000 a healthy router typically holds: the question is not "is the network healthy" but "are we short of the peers selection would otherwise use". Only then is trading recency for pool thickness the right trade.

      • seedProvenResponders

        static void seedProvenResponders(RouterContext ctx, long now)
        Seed the proven-responder map with random peers from the router's peer profiles when the map is below MIN_PROVEN_RESPONDER_COUNT. At cold start (after router restart or long idle period) the map is empty, so first-build selection has no proven preference and may pick unreliable peers. Seeding with random high-tier peers provides a warm start that converges to real proven data after the first few builds. Seeded entries use a near-expired timestamp (now - window + 5 min) so they expire quickly and only provide anti-concentration, not a quality boost over truly proven peers. Best-effort; concurrent access is safe.
        Parameters:
        ctx - the router context
        now - current time in ms

      • requiredSignalQuality

        static int requiredSignalQuality(double buildSuccess)
        Which quality of connectivity evidence a candidate must show to be pre-qualified, as a function of how well tunnel building is going.

        This replaces the previous all-or-nothing switch that disabled pre-qualification entirely once build success fell below ATTACK_THRESHOLD. That switch was self-defeating: the peers it admitted were precisely the ones with no connectivity evidence, so they timed out, which depressed build success further and kept the switch off. A live observation of that loop: builds expiring as Hop1.establishedSilent, far ends classified FarEndUnknown at roughly 5:1 over FarEndUnreachable, and build success oscillating in the 29-46% band directly beneath the threshold.

        Under stress the bar is raised, not lowered. QUALITY_STRICT accepts only a recent successful test or a live transport session — the evidence that a peer is actually reachable — whereas QUALITY_RELAXED additionally accepts mere recent contact or an old favourable acceptance ratio. Requiring more proof when builds are failing is the correct response: a collapse means the marginal peer we can still reach is worth more than the marginal peer we merely hope is reachable.

        Exploratory pools and the startup grace period never pre-qualify at all, so they do not consult this.

        Parameters:
        buildSuccess - the tunnel build success ratio in [0.0, 1.0]
        Returns:
        QUALITY_STRICT when build success is at or below ATTACK_THRESHOLD, otherwise QUALITY_RELAXED

      • windowMultiplierFor

        public static int windowMultiplierFor(int fastPeers, boolean startupGrace, int min, int max)
        Multiplier the peer-supply signal earns, independent of any build-outcome metric. This is the single gate on widening the activity window, shared by the Tuner param, the pool starvation bypass and getActivityWindow(RouterContext) so the three cannot drift apart.

        Rules, in order:

        public static void publishWindowMultiplier(RouterContext ctx)
        Publish the current activity-window multiplier.
