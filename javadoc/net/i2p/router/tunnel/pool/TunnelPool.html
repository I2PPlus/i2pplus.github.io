        A pool normally replenishes toward getEffectiveTarget(): enough tunnels to serve traffic. That is the right target most of the time, but it is blind to a second question. The result is an inbound pool that looks healthy by count and cannot sign a LeaseSet worth publishing.

        This field bridges that gap, by way of pruning only. RepublishLeaseSetJob raises it when a mint is imminent and the pool cannot supply viable leases; pruneExcessTunnels() then offers up tunnels that can no longer be advertised, dropping the pool below its target and so provoking the rebuild. It is deliberately NOT a build target: the required count is at most 2 and getActiveTarget() is at least 2, so folding it into getEffectiveTarget() as a floor could never move the number. Build pressure comes from the shortfall, not from inflating the target.

        The alternative to pruning here is raising LEASE_MIN_REMAINING_MS permanently, which buys the same effect by making every tunnel past a fixed age ineligible -- sustained extra build load on a path that is already denied most of its demand.

      • selectTunnelForTest

        TunnelInfo selectTunnelForTest()
        Select a tunnel to serve as a test round's partner, preferring partners that have demonstrated they work.

        Distinct from selectTunnel(), which serves the live data path and must keep its uniform-random choice: changing that would alter which tunnel carries real traffic, which is well outside what a diagnosis warrants. This is used only where a test round picks the leg its reply comes back through.

        A test round is a composite of the tunnel under test and the partner the reply arrives through, and a single pass/fail bit cannot separate them. Choosing partners uniformly at random therefore injects a source of noise that looks exactly like a failing tunnel: a partner whose gateway has gone quiet since the tunnel was built still satisfies every status gate, because those gates inspect the tunnel and never its peers. Ranked preference costs nothing and cannot reject a working partner, because every tier falls through to the existing behaviour.

        Preference order, best first:

        1. tested GOOD and carrying recent real traffic — the only tier that proves the tunnel works end to end, since receiving data means its gateway is delivering
        2. tested GOOD
        3. carrying real traffic, status not yet known
        4. anything passing the scan gates (the previous behaviour)

        Deliberately a preference and not a filter. A transport-level reachability probe on the gateway was considered and rejected: the gateway is a peer we may hold no session with, or an established but idle one, so treating "not established" as disqualifying would discard good partners and could make the round trip worse.

        Returns:
        the chosen tunnel, or null if none passes the scan gates

      • isLocalHopUnreachable

        private boolean isLocalHopUnreachable(TunnelInfo t)
        Whether this tunnel's local path is unusable because we hold no transport session to the peer we actually send through.

        A tunnel is a crypto path above the transport, and it resolves its hop per message. So when a transport session dies the TunnelInfo and its lease survive untouched: nothing marks the tunnel failed, and getHealthyTunnelCount() -- which tests only expiration, test status, soft failures and next-hop backlog -- keeps counting it. The result is a zombie that occupies a pool slot and inflates every healthy/usable figure the pool and its throttles are driven by, while carrying nothing.

        The peer index is direction-dependent, which is the trap here. Mirroring BuildRequestor.getBuildRequestPeer: for an inbound tunnel getPeer(0) is the peer we send to, but for outbound getPeer(0) is the gateway we want to reach and getPeer(1) is our next hop. Checking getPeer(0) unconditionally would query a session we never had for every outbound tunnel and mark them all dead.

        Only the local hop can be checked. Hops beyond it are inside the network and are reached through the tunnel, so we hold no session to them; a failure there is indistinguishable from a far-end failure. That limit is why this is a complement to the tester rather than a replacement for it.

        A tunnel is only excluded when its local session has been lost since it was built, never merely absent. TunnelInfo.hadLocalHopSession() snapshots the state at addTunnel(TunnelInfo), when the session must have existed for the build to complete. Reading isEstablished on its own cannot tell a genuine zombie from a session that is still coming up, and with the observed exclusion rate near 20% of pool slots that distinction is the difference between measuring real loss and measuring our own reconnects.

        Parameters:
        t - the pool tunnel; may be null or zero-length
        Returns:
        true when the local path cannot carry anything

      • alreadyCondemned

        static boolean alreadyCondemned(boolean isDead, TunnelTestStatus status)
        Whether a failure report is a repeat of a condemnation already made.

        A condemned tunnel is retained until it expires and is replaced immediately, so it keeps receiving work and keeps reporting failures for its whole remaining lifetime. Re-processing those reports only re-logs, asks the pool for a replacement it already has, and lets the failure counter of a retained tunnel climb without bound.

        The test is "would fail() change anything", not "is this the terminal state". A soft-only cascade marks the tunnel FAILING and leaves it there; requiring the hard counter to be tripped as well meant a retained-but-soft-failing tunnel was re-condemned on every subsequent status-3 timeout, and the observed effect was one WARN per failure with the count running past a thousand on a single tunnel inside an hour.

        isDead - whether the tunnel's hard failure counter is tripped
        status - the tunnel's current test status, may be null
        Returns:
        true when this report adds nothing

      • clearFailingOnTraffic

        public void clearFailingOnTraffic()
        Clear FAILING/FAILED flags on tunnels that have provably carried real traffic recently. Data that actually moved through the tunnel is stronger evidence than a tunnel test, so the tunnel has not failed and must stay selectable and in the pool. A test failure on such a tunnel is a reply-path false negative.

        Proof is direction-neutral: InboundEndpointProcessor stamps only after the tunnel's crypto verified, and OutboundClientMessageOneShotJob's SendSuccessJob stamps only after the remote peer replied to the message. Neither dispatch nor a bare gateway accept reaches either call site, so the old inbound-only restriction no longer describes what the marker means.

        FAILED (3+ consecutive failures) is dead and is NOT cleared here. A traffic stamp proves one packet got through, which is not evidence against three consecutive failed tests; only a real passing test (or a rebuild) returns a dead tunnel to service. FAILING (1-2 failures) is transient by definition and clears on a single proof. A genuinely dead tunnel stamps neither marker, so it stays FAILING/FAILED, is excluded from getUsableTunnelCount() and getHealthyTunnelCount() while marked, and ages out at natural expiry — retention cannot strand it as usable.

        UNTESTED tunnels that have delivered verified bytes are promoted to GOOD outright as well. A tunnel that received real end-to-end traffic is proven to work — waiting for a TestJob that may never be scheduled (the fresh tunnel can sit UNTESTED until expiry while the pool keeps rebuilding replacements) means the published LeaseSet stays thin even though usable tunnels are standing. Promoting proof-of-traffic UNTESTED tunnels lets LeaseSet building see them immediately. Verified-bytes is required for UNTESTED (not just recency) because such a tunnel has never passed an explicit test, so its only proof is actual data arrival.

        Called from the periodic pool maintenance sweep (~15s).

        private boolean shouldSkipDueToInProgress(int safeActive, int target, int inProgress, double timeoutRate)
        Variant taking the build timeout rate, which the hot path already has.

      • expirationWithStagger

        private long expirationWithStagger(long now)
        Expiration for a new tunnel, staggered to prevent all tunnels expiring simultaneously. With an 11-min lifetime, un-staggered tunnels across many pools all expire at ~11 min, causing ExpireJob.phase1 to remove them all in one batch → mass EMERGENCY triggers → build storm → death spiral.
