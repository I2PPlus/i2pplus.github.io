    Base I2P tunnel server for handling incoming connections.

    I2PTunnelServer is the foundation for all I2P server tunnels that accept incoming I2P connections and forward them to local TCP services. It manages the lifecycle of I2PSocketManager, handles connection acceptance, and provides connection forwarding to configured local destinations.

    Key Features:

    • Accepts incoming I2P connections via I2PServerSocket
    • Forwards connections to configurable local TCP destinations
    • Supports SSL/TLS connections via I2PSSLSocketFactory
    • Provides port-based destination mapping (targetForPort.xx)
    • Implements connection filtering via StatefulConnectionFilter
    • Uses thread pool for concurrent connection handling

    Connection Flow:

    1. Client connects to I2P destination via I2PServerSocket
    2. blockingHandle(I2PSocket) is called with the I2PSocket
    3. Local TCP socket is created via getSocket(Hash, int)
    4. I2PTunnelRunner handles bidirectional data streaming

    Subclasses: I2PTunnelHTTPServer, I2PTunnelIRCServer, and others extend this class to provide protocol-specific handling while reusing the core connection management infrastructure.

        public void setReadTimeout(long ms)
        Set the read idle timeout for newly-created connections (in milliseconds). After this time expires without data being reached from the I2P network, the connection itself will be closed.

        Less than or equal to 0 means forever. Default -1 (forever) as of 0.9.36 for standard tunnels, but extending classes may override. Prior to that, default was 5 minutes, but did not work due to streaming bugs.

        static boolean acquireConnectionSlot(int maxConnections, AtomicInteger active)
        Decide whether a concurrent-connection slot is available and, if so, reserve it.       • shouldRejectOnQueue

        static boolean shouldRejectOnQueue(int queueDepth, int capacity, int active, int threads, long avgHandleMs)
        Decide whether a connection should be rejected because the handler queue is already drowning. Pure decision, no router context: called from the accept loop after accept() and before a handler thread is consumed.

        Admission policy (high throughput, minimal drops):

        • Hard stop near queue capacity (would hit AbortPolicy anyway).
        • If any handler thread is free, admit — the backlog drains as soon as work is submitted; rejecting while capacity exists only creates empty responses the browser reports as failures.
        • Only when the pool is fully busy is a drain-time estimate applied: queueDepth * avgHandleMs / threads. Reject only when that exceeds MAX_QUEUE_DRAIN_MS, so short bursts queue and drain instead of being dropped, while a hopeless backlog fails fast rather than pinning sockets for minutes.
        Parameters:
        queueDepth - current queued task count
        capacity - total queue capacity; <= 0 disables this gate
        active - currently busy handler threads
        threads - pool max threads; <= 0 disables this gate
        avgHandleMs - average handler time in ms; <= 0 uses DEFAULT_HANDLE_MS
        Returns:
        true if the connection should be rejected with a 503

      • effectiveWriteTimeout

        static long effectiveWriteTimeout(Properties props)
        Determine the write timeout to bind the outbound I2P stream to, in ms.

        A stalled peer (send window not advancing, e.g. under a SYN flood) otherwise holds a server handler thread for the full streaming disconnect timeout (default 120s) inside MessageOutputStream.flush() /close(). Bounding the write timeout fails on no ACK progress rather than blocking the handler; it does not cap throughput for a peer that is progressing, so it is safe for legitimate slow transfers.

        If either the tunnel's own key (PROP_WRITE_TIMEOUT) or the streaming standard key (I2PSocketOptions.PROP_WRITE_TIMEOUT) is present, honor it: return a negative value so the caller leaves the socket options' value untouched (explicit tuning wins, including 0 meaning the unbounded streaming default). Otherwise return the bounded default so unconfigured tunnels are protected.

        Parameters:
        props - the tunnel's client options; may be null
        Returns:
        the write timeout in ms to apply, or negative to apply none

      • run

        public void run()
        Runs the I2PTunnelServer to accept and handle incoming connections asynchronously.

        Accepts connections in a loop, submitting each to the thread pool via CompletableFuture. Handles expected exceptions with retries and logs errors. On shutdown, gracefully terminates the pool.

      • blockingHandle

        protected void blockingHandle(I2PSocket socket)
        This is run in a thread from a limited-size thread pool via Handler.run(), except for a standard server (this class, no extension, as determined in getUsePool()), it is run directly in the acceptor thread (see run()).

        Handles an incoming I2P connection by forwarding it to the local TCP destination.

        This method is called by the server socket's acceptance thread when a new I2P connection arrives. It creates a local TCP socket connection and spawns an I2PTunnelRunner to handle bidirectional data streaming between the I2P and TCP connections.

        Implementation Notes:

        • Subclasses that override this must call super.blockingHandle() or implement full connection handling themselves
        • For protocol-specific handling (HTTP, IRC), spawn a handler thread and return
        • For simple forwarding, this base implementation handles all cases
        • Performance: local connections are fast enough to handle synchronously

        Error Handling: SocketException and IOException are caught and logged, with the socket being reset to notify the peer of the failure.

        Parameters:
        socket - the incoming I2P connection from a remote peer; never null

      • getSocket

        protected Socket getSocket(Hash from, int incomingPort) throws IOException
        Creates a TCP socket connection to the configured destination.

        This method resolves the target host and port for the incoming connection, supporting port-based destination mapping via the client options. If a port has a specific mapping (targetForPort.xx=host:port), that destination is used; otherwise, the default remoteHost and remotePort are used.

        Port Mapping Configuration:

        targetForPort.80=localhost:8080
targetForPort.443=localhost:8443

        Special Ports: Ports 443 and 22 are automatically flagged for non-SSL handling to prevent SSL-over-SSL issues.

        Parameters:
        from - the hash of the peer's destination; used for local address binding
        incomingPort - the port on which the I2P connection was received
        Returns:
        a connected TCP Socket to the appropriate local destination
        Throws:
        IOException - if the socket cannot be created or connected
