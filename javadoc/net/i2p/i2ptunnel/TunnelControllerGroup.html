    ClientApp
    public class TunnelControllerGroupextends Object implements ClientApp
    Coordinates tunnel groups within the JVM, managing configuration persistence.

    Loads and stores tunnel configurations to disk, builds new tunnels on request. Entry point from clients.config.

      • SERVER_HANDLER_IDLE

        static final int SERVER_HANDLER_IDLE
        Worker threads kept for a server tunnel that is currently serving nothing. Deliberately 1, not SERVER_HANDLER_FLOOR: a fixed floor is charged against every open server tunnel before any demand weighting is applied, so on a router with many eepsites it consumed almost the entire budget and left the busiest tunnel with a handful of threads while it rejected connections. An idle tunnel costs one thread and grows on its own demand.

      • setClientRunnerMax

        public static void setClientRunnerMax(int val)
        Clamp and set the maximum concurrent client connections, 4 to 16384. The Tuner I2PTunnelClientRunnerMaxParam stays within this same range.

        Enforces a one-way invariant against the Tuner-managed admission gate (clientDefaultMaxConnections): the worker pool may never be shrunk below what the gate admits. Connections are served thread-per-connection with only a short RUNNER_BURST_QUEUE of slack, so every admitted connection needs its own worker; if the runner were allowed to collapse below the gate, bursts would overflow the worker pool and be closed with zero bytes as empty responses. Flooring the runner at the gate keeps admission and serving capacity in the same ballpark; the runner may still grow above the gate to absorb bursts.

      • getServerExecutor

        ThreadPoolExecutor getServerExecutor(I2PTunnelServer server, int threadOverride)
        Get (creating and sizing on first use) the private handler pool for a server tunnel. All pools are sized together so their sum never exceeds the Tuner-managed global budget while each pool respects its per-tunnel ceiling. Registration records the tunnel's explicit i2ptunnel.server.threads cap (or -1 to follow the Tuner-managed default), rebalancing every live pool to make room for the newcomer.

        Tasks are short-lived (µs-scale), so core threads handle bursts via a bounded queue. Overflow throws RejectedExecutionException (AbortPolicy) rather than running the handler inline on the accept thread, so the accept loop can never be pinned by a write-blocked handler, and the rejection is per-port: only the saturated tunnel's own connections are dropped.

        Parameters:

        threadOverride - the per-tunnel thread cap (>=2), or -1 for default
        Returns:

      • noteRunnerIdle

        void noteRunnerIdle(Object key)
        Note that a submit found this pool quiet, and drop a stale elevation if the tunnel has done enough work while quiet to say the burst is over.

        The rule is expressed in work, not seconds: the floor is released once the pool has completed at least elevatedMax tasks since demand last stopped. A wall-clock interval would be arbitrary for a tracker that idles for a second between announce batches and for a browser that idles for a minute between page loads; counting completed work is self-scaling, because the tunnels that get elevated are the ones that can accumulate idle observations quickly.         This is why the method is separate from the grow: the caller's fast path is one atomic queue read, and only a pool that was actually elevated pays for the decay check.

      • allocateServerThreads

        static int[] allocateServerThreads(int budget, int[] desired, int floor)
        Allocate a global server-handler thread budget across the live server tunnels, preserving each tunnel's ceiling (desired) and a shared floor. Pure decision, no router context: lets the Tuner shrink or grow one budget while the per-tunnel pools inherit exactly their share.

        When the ceilings sum at or below the budget, every tunnel gets its ceiling. Above the budget, the excess is cut proportionally (rounded down, remainder to the last tunnel) so the grand total equals the budget exactly and no tunnel falls below the floor — a genuine per-tunnel cap rather than a free-for-all for the aggregate. When the budget cannot cover a floor for every tunnel, the budget is split evenly with at least 1 thread per live tunnel.

        Parameters:
        budget - the global budget; <= 0 yields all zeros
        desired - per-tunnel ceilings (any values; clamped internally)
        floor - the per-tunnel floor; negative treated as 0
        Returns:
        per-tunnel allocation, same length as desired; each entry >= the shared floor whenever the budget allows; the sum equals min(budget, sum of ceilings) except when the budget is smaller than one thread per tunnel

      • serverThreadsForDemand

        static int serverThreadsForDemand(int queueDepth, int active, int cap)
        Worker threads one server tunnel needs, from its own demand alone.

        Each server tunnel is sized independently. There is no global budget to divide, because dividing one is what made the busiest eepsite unusable: every open server tunnel was charged a floor first, so with twenty eepsites the floor consumed the budget and the pool actually serving requests was left with a ceiling of about a dozen threads. It then refused connections outright while nineteen idle eepsites held their reservations. Those idle pools were not consuming threads anyway — allowCoreThreadTimeOut(true) reclaims them after the keepalive — so the budget bought contention and nothing else.

        Sizing is the load itself: every queued task needs a thread and every busy thread already has one, so queueDepth + active + headroom is both the minimum that keeps up and the size at which nothing queues. A dormant tunnel sits at SERVER_HANDLER_IDLE and grows on its own demand. The per-tunnel ceiling still applies, so one destination cannot take the whole machine.

        Pure decision, no router context, so the policy is testable.

        Parameters:
        queueDepth - tasks waiting for a handler thread
        active - handler threads currently busy
        cap - this tunnel's ceiling (override or Tuner default)
        Returns:
        worker threads for this pool, in [1, cap]

      • scaleDemandsToCeiling

        static int[] scaleDemandsToCeiling(int[] demand, int ceiling)

      • createServerExecutor

        static ThreadPoolExecutor createServerExecutor(int threads, AtomicLong index)
        Create a bounded executor that runs inbound server-tunnel connection handlers.

        Handlers are dispatched off the accept thread so a single slow connection cannot stall connection admission. Overflow uses ThreadPoolExecutor.AbortPolicy: when the fixed worker set and its bounded queue are saturated, the submission throws RejectedExecutionException instead of executing the handler inline on the caller. Inline execution (the former CallerRunsPolicy) would run a write-blocked handler on the I2PTunnelServer.run() accept loop, pinning accept(), which stops draining the streaming SYN queue and makes every fresh connection attempt expire and be RESET under load. The rejection is surfaced to I2PTunnelServer.run(), which closes the connection but keeps accepting new ones.

        Exposed package-visible (static) so tests can assert the overflow semantics without a live I2PAppContext.

        Parameters:
        threads - the fixed core/max worker count
        index - an AtomicLong counter used to name worker threads
        Returns:
        a never-null, bounded executor with AbortPolicy
