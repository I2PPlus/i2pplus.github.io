    public class I2PTunnelHTTPServerextends I2PTunnelServer
    HTTP server tunnel that filters headers and provides compression.

    Extends I2PTunnelServer to filter HTTP headers from client to server, replacing the Host header with configured value. Compresses HTTP message body and sets Content-Encoding: x-i2p-gzip when browser requests Accept-Encoding: x-i2p-gzip.

    Features include POST/PUT rate limiting, referer and user-agent rejection, inproxy detection, HTTP blocklist support, keepalive management, and response header security filtering.

      • maxIOThreads

        public static int maxIOThreads()
        Heap-derived ceiling on the I/O transfer budget.

        Each I/O thread holds 16 KB of buffer plus a 16 KB BufferedInputStream and is blocked for the whole of a body transfer, so a thread costs roughly an order of magnitude more than a runner-pool task, which finishes in microseconds. Costing the divisor accordingly: 4 MB per thread rather than the 2 MB the runner pool uses. At 8 GB that is 2048 threads, adding roughly 190 MB to a 1.2 GB footprint — comfortable, and still large headroom over the few hundred concurrent transfers a 40 K-client tracker produces at a 30-minute announce interval.

        The ceiling is burst headroom, not residency: allowCoreThreadTimeOut with a 30-second keepalive reaps threads half a minute after their last task, so an idle pool costs nothing whatever the ceiling says.

        Returns:
        the memory-feasible I/O thread ceiling, in [1024, 16384]

      • computeStallWindowMs

        static long computeStallWindowMs(long baseMs, long bytesTransferred)
        Stall window for a body that has already moved bytesTransferred.

        The configured window is right for a small response but wrong for a bulk one: over a congested path a 45MB transfer routinely pauses for many seconds between copy steps, and a single fixed window either kills the transfer or, if sized for the bulk case, pins a worker for minutes behind a dead peer.       • classifyStalledSide

        static String classifyStalledSide(long readAgeMs, long writeAgeMs, long bytesTransferred)
        Which side of a stalled body transfer stopped making progress.

        Read and write stamps are updated either side of the same copy step, so a body blocked mid-write ages both equally: the read that fed the blocked write is stamped, then the write never completes to stamp itself. The two therefore look identical to a body blocked mid-read, and only the progress counter separates them -- a body that has moved meaningful bytes and then gone quiet is sitting in a blocked write, because a blocked read would have had nothing to hand the previous write.

        Reporting the ambiguous case as the source is actively misleading: a 45MB download that stalled after 3.2MB was logged as "local backend silent" while the same backend served the whole file in 4ms on a fresh connection, sending every diagnosis to the wrong layer.

        Parameters:
        readAgeMs - age of the last-read stamp
        writeAgeMs - age of the last-write stamp
        bytesTransferred - bytes already moved by the body
        Returns:
        one of STALL_SIDE_SOURCE, STALL_SIDE_DESTINATION, or STALL_SIDE_INDETERMINATE
