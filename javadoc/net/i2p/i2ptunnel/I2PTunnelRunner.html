    Thread that forwards traffic between an I2PSocket and a TCP Socket.

    I2PTunnelRunner implements the core bidirectional data forwarding between I2P and TCP network connections. Operates two StreamForwarders: the I2P to TCP direction runs inline and the TCP to I2P direction runs concurrently via a shared executor pool.

    Connection Flow:

    1. Runner is created with connected I2PSocket and TCP Socket
    2. Initial data may be sent immediately via initialI2PData/initialSocketData
    3. Two StreamForwarders run for bidirectional streaming; TCP to I2P via executor pool
    4. Runner monitors both connections for errors or disconnection
    5. On completion or failure, callbacks may be invoked and sockets are closed

    Keep-Alive Support: When keep-alive is enabled for either connection, the runner may skip spawning one direction of forwarding if no data is expected. This optimization is used for simple GET requests that don't require responses.

    Thread Safety: This class uses locks (slock) to coordinate socket access and prevent concurrent writes from multiple threads. The finishLock ensures thread-safe state transitions.

      • MAX_EMPTY_RECONNECT_CYCLES

        static final int MAX_EMPTY_RECONNECT_CYCLES
        Max number of consecutive no-progress cycles (stalls) the outer empty-response / body-resume reconnect loop may invoke the callback for. The callback's own for-loop handles connect-failure backoff, but when the destination is reachable yet always sends zero bytes, each cycle succeeds on attempt 1 and the outer loop would spin forever. This is the baseline for entities under RETRY_RAMP_UNIT_BYTES; stallCycleLimit(long) ramps the cap by one cycle per 1MB of Content-Length so a large file can outlive proportionally more tunnel-pool churn. A cycle that makes any forward progress on the entity body resets this budget (see MAX_RESUME_CYCLES).

      • MAX_RESUME_CYCLES

        static final int MAX_RESUME_CYCLES
        Absolute safety cap on total body-resume cycles regardless of progress. Progress resets the stall budget (MAX_EMPTY_RECONNECT_CYCLES) so a slowly-advancing transfer is never abandoned mid-body for lack of progress, but a pathological trickle (one byte per cycle forever) must still terminate. Well above any legitimate need: a healthy resume completes in 1–2 cycles.

        static final int SCALED_CAP_MULTIPLIER

      • RESUME_DEADLINE_MS

        static final long RESUME_DEADLINE_MS
        Wall-clock ceiling on one entity's resume/reconnect sequence (ms), independent of Content-Length.

        The cycle caps in stallCycleLimit(long) and totalCycleLimit(long) bound attempt count, but each attempt may block for a full connect timeout, so a large entity's 29x-scaled budget can keep a runner busy for hours against a destination that is answering but never finishing. This deadline is the only bound expressed in the unit the browser actually waits in.

        Set well above what the baseline caps can consume (4 empty-reconnect cycles, each bounded by a connect timeout) so ordinary small-entity reconnects are never cut short; it only bounds the size-scaled ramp.

        See Also:

      • RETRY_RAMP_MAX_BYTES

        static final long RETRY_RAMP_MAX_BYTES
        Largest Content-Length that may enlarge the retry ramp (bytes).

        The ramp exists because a genuinely long transfer survives proportionally more tunnel-pool churn than a small file. A Content-Length beyond this is not a long transfer, it is an upstream claim no honest peer makes, and it must not be able to buy extra retry budget: the cap is already saturated long before this size, so clamping the input costs nothing real and denies a hostile or broken destination the largest rung of the ladder.

      • onNoDataFailure

        protected void onNoDataFailure()
        Invoke the no-data failure callback when a transfer completes (or aborts) without delivering any bytes from the I2P peer.

        This is the single choke point behind the "empty response" class of bugs: without it, a connection that is established to the proxy but never yields an upstream byte (server unresponsive, reset before first data, or the executor rejecting the forwarder) would end by closing the local socket with nothing written, which the browser reports as NS_ERROR_NET_EMPTY_RESPONSE. The HTTP client runner wires its I2PTunnelRunner.FailCallback to a handler that writes a well-formed HTTP error page to the browser socket before closing; this is what turns a silent empty close into a surfaced 5xx. The base implementation simply dispatches to the configured I2PTunnelRunner.FailCallback or onTimeout.

        Safe to call from any completion or exception path; _noDataHandled guarantees the callback runs at most once even when several paths race. Run even when totalSent > 0 (post body) — the absence of a response is still a failure. Never run when any upstream bytes were received.

      • resumeIncompleteBody

        private void resumeIncompleteBody(OutputStream out)
        Resume an incomplete Content-Length body on a fresh I2P connection.

        Rotates to a new tunnel via I2PTunnelRunner.ReconnectCallback, re-sends the buffered GET/HEAD with Range: bytes=N- for the undelivered remainder, and splices the second response body onto the browser stream without re-emitting headers. After a transient status (408/502/503/504) aborts a Range attempt the stream can no longer splice, so the next attempt re-requests the full entity with all Range headers stripped; the fresh 200's already-delivered prefix is then dropped so the splice stays seamless. The budget is progress-based: only consecutive stall cycles (no new body bytes since the previous attempt) count against the size-scaled cap from stallCycleLimit(long) (baseline MAX_EMPTY_RECONNECT_CYCLES); any forward progress resets that counter so a slowly-advancing download is never abandoned for lack of progress. totalCycleLimit(long) is an absolute safety cap on total attempts regardless of progress.

        Parameters:
        out - browser-facing output stream

      • trackInitialResponseDeadline

        protected boolean trackInitialResponseDeadline()

      • noteRequestWritten

        void noteRequestWritten()
        Record a request-side write upstream: start (or slide, or restart) the first-response deadline for the current attempt. Sliding on every toI2P write keeps a slow POST upload from tripping the deadline; a re-send after an empty response restarts it for the fresh attempt. Clears the fired latch so the new attempt may fire independently.

      • checkInitialResponseDeadline

        boolean checkInitialResponseDeadline(long nowMs)
        Enforce the first-response deadline: close the I2P socket if no response byte arrived within initialResponseTimeoutMs of the last request-side write. Closing the socket is what unblocks the receive forwarder (a blocked read throws once the stream closes), and run()'s existing empty-transfer path then invokes the no-data failure callback — the single choke point — so the browser sees a proper 5xx instead of an indefinite hang. At most one close per request attempt; a subsequent re-send re-arms via noteRequestWritten().
        Parameters:
        nowMs - current epoch-ms, from System.currentTimeMillis()
        Returns:
        true if the socket was closed by this call
