    net.i2p.data.DataHelper
    public class DataHelperextends Object
    Comprehensive utility class for I2P data structure serialization, encoding, and manipulation.

    DataHelper provides essential utilities for working with I2P data structures:

    • Serialization: Read/write primitive types to/from streams
    • Encoding: Hex encoding/decoding (Base64 and Base32 live in their own classes)
    • Validation: Data format verification and bounds checking
    • Conversion: Between different data representations
    • Utilities: Common operations on collections and arrays

    Core Operations:

    • Primitive I/O: readLong(InputStream, int), writeLong(), readString(), writeString()
    • Hex: toHexString(byte[]), fromHexString() for display and debugging
    • Properties: readProperties(InputStream), writeProperties() for metadata
    • Collections: toMap(), Object.toString() for data structures

    Encoding Support:

    • Base64/Base32: provided by the Base64 and Base32 classes, not here
    • Hex: Hexadecimal encoding for debugging and display
    • UTF-8: String encoding with proper byte handling

    Data Structure Support:

    • Arrays: Efficient reading/writing of byte arrays
    • Collections: Map, List, and Set serialization
    • Dates: Timestamp handling with proper timezones
    • Properties: Key-value pair serialization

    Validation and Safety:

    • Bounds Checking: Prevent buffer overflows and underflows
    • Null Handling: Safe null value processing
    • Size Limits: Protection against excessive memory allocation
    • Format Validation: Data structure integrity checks

    Performance Features:

    • Buffer Reuse: ByteArrayStream for efficient operations
    • Caching: Frequently used constants and computations
    • Bulk Operations: Optimized for large data sets
    • Memory Management: Careful allocation and cleanup

    Common Use Cases:

    • Network Protocol: I2NP message serialization
    • Configuration: Properties file handling
    • Address Display: via the Base32 class for .b32.i2p
    • Data Storage: File format serialization
    • Debugging: Hex dumps and data inspection

    Thread Safety:

    • Static Methods: All operations are thread-safe
    • No State: Class maintains no mutable instance state
    • Immutable Data: Input data is not modified

      • readProperties

        public static Properties readProperties(InputStream rawStream) throws DataFormatException, IOException
        Read a mapping from the stream, as defined by the I2P data structure spec, and store it into a Properties object.

        A mapping is a set of key / value pairs. It starts with a 2 byte Integer (ala readLong(rawStream, 2)) defining how many bytes make up the mapping. After that comes that many bytes making up a set of UTF-8 encoded characters. The characters are organized as key=value;. The key is a String (ala readString(rawStream)) unique as a key within the current mapping that does not include the UTF-8 characters '=' or ';'. After the key comes the literal UTF-8 character '='. After that comes a String (ala readString(rawStream)) for the value. Finally after that comes the literal UTF-8 character ';'. This key=value; is repeated until there are no more bytes (not characters!) left as defined by the first two byte integer.

        As of 0.9.18, throws DataFormatException on duplicate key.

        Parameters:
        rawStream - stream to read the mapping from
        Returns:
        an OrderedProperties holding the pairs read from the stream, whose key set and entry set iterate in lexicographical key order rather than stream order
        Throws:
        DataFormatException - if the format is invalid
        IOException - if there is a problem reading the data

      • messageOf

        public static String messageOf(Throwable t)
        The throwable's message, never null.

        Throwable.getMessage() returns null routinely, and not only for exotic exceptions: a stream that dies mid-read produces an IOException with no message at all. Four sites in the HTTP server and client tunnels called getMessage().indexOf(...) on it anyway, and each threw a NullPointerException from inside its own catch block - which replaced the diagnostic it was trying to log with a stack trace, and left the original failure unexplained.

        Falls back to the throwable's class name, because "what failed" is recoverable from the type even when there is no message, whereas the bare string "null" would make two different failures read identically in a log.

        Parameters:
        t - the throwable, which may be null
        Returns:
        the message, or the simple class name when there is none, or the empty string when the throwable itself is null
