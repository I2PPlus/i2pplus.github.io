    java.lang.Object
    net.i2p.util.SimpleTimer2
    public class SimpleTimer2extends Object
    Scheduled event executor backed by ScheduledThreadPoolExecutor. Replaces the legacy SimpleTimer (deleted; had lock contention issues). Supports cancel and reschedule. Events must NOT block.

    All timer events should extend TimedEvent and use schedule(SimpleTimer2.TimedEvent, long)/cancel() directly.

    A saturation watchdog samples this pool from a thread of its own and warns when every worker has stayed occupied with a backlog behind it: a ScheduledThreadPoolExecutor never grows past DEFAULT_THREADS, so two blocked events starve every periodic event on this timer without throwing anything or writing anything to the log.

    • Field Details

      • DEFAULT_THREADS

        static final int DEFAULT_THREADS
        Default worker count. Two was the original value and is enough only while the timer's total event volume stays below what two threads can service: the pool never grows past this figure, so a persistent backlog shows up as execution latency rather than as a rejected task or a warning anywhere else.

        A live router measured a 16s median / 30s p90 execution delay across many event types - ACKTimer, KillTimer, BodyWatchdog, DelayedCloser, Cleaner, RemoveExpired - which is the signature of a volume-saturated pool rather than of the two-blocked-events wedge the saturation watchdog exists to catch. That watchdog samples occupancy and queue depth at an instant, so it reports a wedge but is blind to a backlog whose events merely run back-to-back.

      • _immediateReschedules

        private final AtomicLong _immediateReschedules
        Schedules requested with a zero or negative delay since the last watchdog report. Counted rather than logged per event: an immediate reschedule is legitimate occasionally, but a connection whose head-of-line packet is already older than one RTO asks for one on every ACK, and a population of those will bury a two-thread pool. The count is what tells the saturation report the queue is being flooded by immediate reschedules rather than by ordinary periodic work.

        Incremented only on the zero-delay path, so the steady-state cost is nil.

      • desiredThreads

        public static int desiredThreads(int backlogMs, int current, int max, int growMs, int shrinkMs)
        How many workers to run for a given backlog. Pure decision helper for unit tests.

        The trigger and the release are deliberately far apart. A timer that grows at 2s of backlog and shrinks at 1.9s would oscillate between two thread counts for as long as the load sat near the threshold, and every step reallocates threads. Shrinking only on a genuinely clean reading costs a little recovery time and removes the oscillation entirely.

        Parameters:
        backlogMs - the worst recent execution delay in ms, 0 when nothing is late
        current - the worker count now in effect
        max - the ceiling; non-positive falls back to MAX_THREADS rather than being read as "no ceiling", so a caller passing a bad value cannot disable the bound
        growMs - backlog at or above which a worker is added
        shrinkMs - backlog at or below which a worker is released
        Returns:
        the worker count to move to, never below MIN_THREADS and never above the ceiling in force

      • evaluateSaturation

        static SimpleTimer2.WatchdogDecision evaluateSaturation(int activeCount, int poolSize, int queueSize, int consecutiveSaturatedSamples, int threshold, boolean episodeReported)
        Decide what one saturation sample means.

        The pool counts as saturated only when both halves hold: every worker is occupied (activeCount >= poolSize) and at least WATCHDOG_MIN_QUEUE events are waiting behind them. Either half alone is noise - the queue also holds delayed events that are not due yet, and both workers being busy is ordinary whenever two events happen to run at once.

        consecutiveSaturatedSamples counts the samples before this one, so a threshold of N reports on the (N+1)th consecutive saturated sample: "more than N samples", not "N". episodeReported is the throttle, which is what turns a permanently-wedged pool into one WARN instead of one every WATCHDOG_INTERVAL_MS.

        Parameters:
        activeCount - executor active thread count
        poolSize - executor pool size, zero once it is shut down
        queueSize - executor queue depth
        consecutiveSaturatedSamples - immediately preceding saturated samples
        threshold - consecutive saturated samples tolerated before reporting
        episodeReported - whether this episode has already been reported
        Returns:
        REPORT once per episode, OK when not saturated (ending the episode), PENDING otherwise

      • evaluateStall

        static SimpleTimer2.WatchdogDecision evaluateStall(long completed, long lastCompleted, int consecutiveStalledSamples, int threshold, boolean episodeReported, long maxObservedGapMs)
        Decide what one "nothing finished" sample means.

        This is the cheap form of "a periodic event stopped firing": the executor's own completed-task counter not advancing across samples means nothing this timer runs is finishing, regardless of what the pool size says. It deliberately does not track individual events - that would mean bookkeeping on every scheduling and every run.

        An executor that has never completed a task is treated as idle, not wedged: a timer with nothing scheduled on it is not a failure, and warning about one would bury the real reports. A wedge that starts before the first completion is still caught by evaluateSaturation(int, int, int, int, int, boolean).

        The quiet period is calibrated against the timer's own worst observed gap rather than its mean interval. A mean is the wrong statistic here: a coalescing timer runs in dense bursts, so its mean interval is dominated by the busy stretches while the real gaps between bursts run far longer. Scaling the bar by a multiple of the mean therefore trips on healthy bursty timers, which trains the reader to ignore the one report that matters. The longest gap a timer has actually come back from is self-calibrating, and it reports only a quiet period that exceeds what that timer has done before.

        Parameters:
        completed - executor completed task count, now
        lastCompleted - executor completed task count, at the previous sample
        consecutiveStalledSamples - immediately preceding samples with no progress
        threshold - such samples tolerated before reporting
        episodeReported - whether this episode has already been reported
        maxObservedGapMs - longest quiet period this timer has previously come back from; zero when no baseline has been established
        Returns:
        REPORT once per episode, OK on progress or an idle timer (ending the episode), PENDING otherwise
