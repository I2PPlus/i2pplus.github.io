      • SYSTEM_LOAD_CACHE_MS

        static final long SYSTEM_LOAD_CACHE_MS
        Minimum interval between two OS queries for the system load average. getSystemLoadAverage() is a native call (JDK reads /proc/loadavg), far more expensive than a map lookup, and it sits on the per-build-request path of both tunnel throttlers. The load average is itself a 1/5/15 minute metric, so 1s of staleness is far below its own resolution.

      • getCPULoad

        public static int getCPULoad()
        Retrieve CPU Load of the JVM.

        The MXBean query is expensive — on JDK 19+ each call reads /proc via Files.lines. So results are cached for CPU_LOAD_CACHE_MS. Callers such as the JobQueue pumper and the throttlers only need a coarse periodic sample, so up to 1s of staleness is acceptable.

        Returns:
        the CPU load

      • sysLoadCacheStale

        static boolean sysLoadCacheStale(long lastQueried, long now)
        Whether the cached system load sample is old enough to refresh. Never-queried (lastQueried == 0) counts as stale so the first call always queries the MXBean instead of returning the 0 initializer. A wall-clock step backwards (NTP correction, manual change) also counts as stale: a plain age comparison would report the sample as fresh until the clock caught up again, pinning a stale value for the length of the step.

        lastQueried - the wall-clock ms of the previous query, or 0
        now - the current wall-clock ms
        Returns:
        true if the cache should be refreshed

      • getTunnelBuildSuccessRatio

        public static double getTunnelBuildSuccessRatio(StatManager sm, int windowMs)
        The canonical tunnel build success ratio: successes over all settled builds, 0.0 to 1.0, for a stated window.

        This is the single source of truth. Three implementations existed and none of them agreed: ProfileOrganizer read getCurrentEventCount() - the current partial period - while asking for the ten minute rate, so it sampled a fraction of one bucket and threw the history away; the copy here read getLastEventCount(), the last completed period; and the Tuner used a different set of stats entirely on an hourly window. That value is not cosmetic - it gates profile eviction, selects the ghost cooldown, and feeds ClientPeerSelector first-hop selection - so a partial-period reading could intermittently drop it under the attack threshold and switch all three to their defensive behaviour on noise.

        Counts events over the last completed window rather than the current partial one, so the reading does not depend on where in the period it was sampled. Partial-period sampling was what made the old value swing, and swing under the attack threshold, which switches off profile eviction and lengthens ghost cooldowns.

        Parameters:
        sm - the stat manager, or null
        windowMs - the averaging window in milliseconds
        Returns:
        the ratio, or NaN if the stats are absent or the window is empty
