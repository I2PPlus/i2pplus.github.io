      • _keySpecs

        private final Map<SessionKey, SecretKeySpec> _keySpecs
        Memoized SecretKeySpec per SessionKey for the system-AES path.

        Why memoize at all: building the spec clones the key material, but SecretKeySpec.getEncoded() returns the spec's *internal* array, so a reused instance passes the same byte[] reference to Cipher.init(int, Key) and skips JCE makeSessionKey re-expansion of the 256-bit key on every JVM-path encrypt/decrypt.

        This cache is deliberately NOT the same as SessionKey.getPreparedKey(), which is owned by the legacy Cryptix path and lives per SessionKey - keep the two fast paths decoupled. SessionKey equality is value-based, so distinct-but-identical keys share one spec (their bytes are equal, so sharing is correct).

        DO NOT make this map access-ordered: with accessOrder=true, get() counts as a structural modification, so every lookup would need a lock and that would serialize every AES op of at least MIN_SYSTEM_AES_LENGTH bytes across the whole router. Insertion order keeps lookups lock-free and eviction drops the eldest, not the coldest.

      • _keySpecReads

        private final ConcurrentMap<SessionKey, SecretKeySpec> _keySpecReads
        Lock-free read side of the _keySpecs memo. Written only inside the synchronized(_keySpecs) miss path, so it is always a mirror of _keySpecs (plus, transiently, the entry being evicted). Bounded by the same KEY_SPEC_CACHE_SIZE.

      • hasAESNI

        private static boolean hasAESNI()
        Check for AES support in processor and JVM.

        On x86-64 this consults CPUID when libjcpuid is available; a missing helper library must not silently disable the JDK path, so the JDK's own implementation (AES-NI intrinsics where present, tables otherwise) is assumed instead - it is at least as good as the bundled Cryptix tables. On other 64-bit ABIs (notably AArch64, which has AES in the base ISA) the JDK path is used as well. 32-bit and non-mainstream JVMs keep the Cryptix tables.

        Returns:
        whether the JDK Cipher path should be used

      • getKeySpec

        SecretKeySpec getKeySpec(SessionKey sessionKey)
        Get (or build and remember) the SecretKeySpec for a session key. Package-visible so the unit tests can verify reuse, longevity across sessions and the size bound.

        The hit path is lock-free: a ConcurrentHashMap lookup only. The miss path takes synchronized(_keySpecs) - that is the only place the KEY_SPEC_CACHE_SIZE bound is enforced, by evicting the eldest entry in insertion order.

      • release

        private void release(Cipher cipher)
        Return the Cipher to the cache without scrubbing it first.

        The pooled Cipher keeps the round keys of the operation that just finished. Re-initializing it with a zero key was dropped because Cipher.init(int, Key) at the next acquire overwrites the schedule anyway, and the extra key schedule is pure overhead. It protected nothing either: the live key bytes are already resident for the life of the SessionKey in the _keySpecReads memo and in SessionKey.getPreparedKey() on the legacy Cryptix path.

        Parameters:
        cipher - the Cipher to return to the cache
