    All Implemented Interfaces:
    Closeable, AutoCloseable
    class MessageInputStreamextends InputStream
    InputStream implementation that accepts messages arriving out of order and presents the data in proper sequence for reading.

    This class buffers incoming data blocks and reorders them transparently, ensuring a continuous byte stream to the caller. It supports:

    • Out-of-order message handling
    • Flow control via blocking reads
    • Optional read timeouts
    • EOF signaling via closeReceived()
    • Error propagation via streamErrorOccurred()

    Thread Safety: This class is synchronized internally and safe for use by one reader thread and potentially multiple message-receiving threads.

    Performance: Designed for high-throughput scenarios such as large file downloads. Avoids unnecessary copying by using ByteArray references.

    Lifecycle: The stream can be closed locally or receive an EOF signal remotely. Once closed, no further reads or message receptions are allowed.

    Usage:

    I2PSession -> MessageHandler -> PacketHandler ->
    ConnectionPacketHandler -> MessageInputStream

      • DUMMY_BA

        private static final ByteArray DUMMY_BA
        Sentinel used for out-of-order duplicates when stream is closed. When locallyClosed is true and an out-of-order message arrives, we store this sentinel instead of the actual payload to prevent memory accumulation while still allowing canAccept(long, int) to return true for retransmits of already-processed messages. This enables proper handling of late-arriving duplicate packets after stream closure.

        Note: the payload size of this sentinel is 0, so it does not count toward _readyDataSize or buffer limits. See canAccept(long, int).

      • decayBufferSize

        static int decayBufferSize(int current, int floor, int peak)
        Decide the receive-buffer cap once the reader has emptied the buffer.

        The peak, not the current level, is the signal: it says how much buffer the drain just finished actually needed. Keeping room for twice the peak means a connection that is genuinely using the larger buffer keeps it, and the cap converges on the working set instead of alternating a grow with a shrink on every burst.

        Parameters:
        current - the cap in effect, in bytes
        floor - the configured size, which the cap never falls below
        peak - most bytes buffered since the previous check, in bytes
        Returns:
        the new cap: half of current clamped to floor, or current if the peak shows the larger buffer is in use

      • decayBuffer

        private void decayBuffer()
        Decay the receive-buffer cap toward the configured size after the reader empties the buffer.

        Without this the cap only ratchets up. One transient burst that trips canAccept() doubles it, and every later packet on that connection is then judged against the larger window for the rest of its life, so the memory stays committed whether the traffic needs it or not.

        Caller must hold _dataLock.
