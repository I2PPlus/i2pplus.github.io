    public class TrackerClientextends Object implements Runnable
    Handles communication with BitTorrent trackers and DHT to discover new peers.

    This class manages tracker announcements and peer discovery by:

    • Announcing torrent status to HTTP/HTTPS trackers
    • Processing tracker responses and extracting peer information
    • Managing UDP tracker communication
    • Integrating with DHT for trackerless peer discovery
    • Handling Peer Exchange (PEX) when available
    • Managing announcement intervals and retry logic
    • Processing various tracker events (started, completed, stopped)

    Threading Model: The start() method creates a thread that runs one complete announcement cycle through all trackers, PEX, and DHT, then queues a new timed event and exits. This approach prevents thread accumulation while ensuring regular announcements.

    The client can be restarted after halt(boolean) and handles various tracker responses including registration failures and error conditions.

      • _unannouncers

        private static final ThreadPoolExecutor _unannouncers
        Unannounces are sent from a shared, bounded pool instead of one thread per tracker, so stopping thousands of torrents cannot exhaust threads. Threads exist only while unannounces are pending and die back after UNANNOUNCE_KEEPALIVE of idle time; the pool is capped at UNANNOUNCE_THREADS, sized to saturate the I2P tunnel (requests are latency-bound, so a few dozen workers drain a burst as fast as the network allows). The bounded queue absorbs the burst; only when the queue and pool are full is the unannounce skipped and the tracker reset, the same degradation as the previous OutOfMemoryError fallback. Threads are daemons, so they never hold up router shutdown.

      • ANNOUNCE_PERMITS

        private static final Semaphore ANNOUNCE_PERMITS
        Global cap on tracker HTTP requests in flight across ALL torrents, so simultaneous announce/scrape rounds cannot stampede a tracker (or our own netdb lookup path) when many TrackerClient threads wake together. Requests beyond the cap queue on the permit; the fetch timeout clock only starts once the permit is held. Increased from 3 to 10 to allow parallel DHT metadata lookups (e.g. zzzot hashlist) while per-tracker throttle below prevents hammering any single tracker.

        Per-tracker throttle: max 20 requests per tracker host per minute. Shared across all torrents to cap load on popular trackers (e.g. postman, torrfreedom) even when many torrents use the same tracker. Guarded by itself.
