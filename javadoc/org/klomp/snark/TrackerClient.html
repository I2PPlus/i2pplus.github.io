    public class TrackerClientextends Object implements Runnable
    Handles communication with BitTorrent trackers and DHT to discover new peers.

    This class manages tracker announcements and peer discovery by:

    • Announcing torrent status to HTTP/HTTPS trackers
    • Processing tracker responses and extracting peer information
    • Managing UDP tracker communication
    • Integrating with DHT for trackerless peer discovery
    • Handling Peer Exchange (PEX) when available
    • Managing announcement intervals and retry logic
    • Processing various tracker events (started, completed, stopped)

    Threading Model: The start() method creates a thread that runs one complete announcement cycle through all trackers, PEX, and DHT, then queues a new timed event and exits. This approach prevents thread accumulation while ensuring regular announcements.

    The client can be restarted after halt(boolean) and handles various tracker responses including registration failures and error conditions.

      • longSleepWithJitter

        static long longSleepWithJitter(long currentInterval, long randomJitter)
        Failure backoff for a tracker that just hit MAX_CONSEC_FAILS: floor the announce interval at LONG_SLEEP and add up to LONG_SLEEP_JITTER of randomness so many torrents failing together don't re-announce in lockstep every 2 minutes. Intervals already at or above the floor and out-of-range random values are handled: the jitter is clamped to [0, LONG_SLEEP_JITTER] and only applied when the floor was raised.
        Parameters:
        currentInterval - tracker's current announce interval in ms
        randomJitter - raw random jitter in ms, before clamping
        Returns:
        the new announce interval in ms

      • normalizeTrackerProblem

        static String normalizeTrackerProblem(String trackerProblem)
        Lower-cases a tracker problem message for prefix matching.

        Never null: several IOException subtypes return a null getMessage(), and the announce loop calls this on the result directly. Letting that NPE escape would abort the announce for every remaining tracker because of one malformed response from the first one.

        Parameters:
        trackerProblem - message from the exception, may be null
        Returns:
        lower-cased message, or the empty string when there was none

      • initialAnnounceDelayMs

        static long initialAnnounceDelayMs(boolean hasMeta, int fullSpread, int magnetSpread)
        Delay before a torrent's first announce.

        Pure decision, separated so the magnet case can be pinned by test: the spread exists to protect the trackers from a thundering herd, and that concern does not apply to a single lookup, which is actively waiting for an answer.

        Parameters:
        hasMeta - true once the torrent has its metainfo
        fullSpread - random value in [0, INITIAL_SLEEP)
        magnetSpread - random value in [0, MAGNET_INITIAL_SLEEP)
        Returns:
        ms to wait before the first announce

      • shouldTryFallbackTrackers

        static boolean shouldTryFallbackTrackers(int peersFromPrimaries, boolean haveBackup, boolean downloading)
        Should the fallback trackers be tried after a round that produced no peers?

        needBackupTrackers(boolean, boolean, boolean, int, boolean) deliberately refuses to consult backups while a primary tracker is configured, which is right for a download that is already finding peers but leaves a magnet with nothing: every announce failed and the next cycle is 90s away. A different transport is the only remaining option, and the caller has already paid for the round that failed.

        Parameters:
        peersFromPrimaries - peers returned by the primary trackers this cycle
        haveBackup - whether any fallback tracker is configured
        downloading - whether the torrent still wants peers
        Returns:
        true if the fallback round should run

      • needBackupTrackers

        static boolean needBackupTrackers(boolean havePrimary, boolean haveBackup, boolean dhtEnabled, int dhtSize, boolean downloading)
        Whether a trackerless torrent should consult its backup trackers this round. A download always does; a seed does only while the DHT is still short of its bootstrap node count, since once the DHT is warm the trackers add nothing.
        Parameters:
        havePrimary - whether any primary tracker is configured
        haveBackup - whether any fallback tracker is configured
        dhtEnabled - whether a DHT instance is running for this torrent
        dhtSize - the number of known nodes in that DHT
        downloading - whether the torrent still wants peers, false for a seed
        Returns:
        true if the backup tracker round should run
